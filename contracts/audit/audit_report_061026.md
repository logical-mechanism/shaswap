## 3. Contract Overview

ShaSwap settles a batch of order UTxOs against one pool UTxO in a single transaction. Batch-wide rules are checked **once per tx** by a withdraw-0 staking validator (`settlement`, the trust anchor `S`); the order and pool spend validators are thin deferrals that ride on `S` being present.

**Validators & policies:**

- **`settlement`** (`validators/settlement.ak`) — unparameterised withdraw-0 staking script. `withdraw` runs `clearing.run` (the whole §5.2 batch check). `publish` permits **only** `RegisterCredential` (never deregister/delegate), so `S` is an immortal, undelegatable anchor. `else -> fail`.
- **`order(S)`** (`validators/order.ak`) — spend. `Settle` defers to `spend.order_settle` (self-checks the input is S-tagged + a withdraw-0 for `S` is present); `Reclaim` is owner verification-key signature only.
- **`pool(S)`** (`validators/pool.ak`) — spend. `PoolSettle` runs `spend.pool_settle` (owns the constant-product `k`-check + price pin); `LpAction` runs `spend.lp_action` guarded by `!withdrawal_present(S)`; `ClosePool` runs `spend.pool_close`.
- **`pool_mint(seed)`** (`validators/pool_mint.ak`) — minting policy parameterised by a seed `OutputReference` (one-shot ⇒ unique NFT). `Create` mints `{NFT:1, LP:total_lp}` into a validated pool UTxO; `Close` is burn-only.
- **`lp_intent(S)`** (`validators/lp_intent.ak`) — spend. `Fulfill` runs `lp_intent.fulfill` (a batcher-fulfilled, single-intent LP deposit/withdraw; asserts `!withdrawal_present(S)`); `ReclaimLp` is owner signature only.

**Protocol flow:** A pool is created by `pool_mint.Create` (mints NFT + full LP supply into one pool UTxO, validates a well-formed external pair). LPs deposit/withdraw via `pool.LpAction` (direct) or via `lp_intent.Fulfill` (batcher-mediated). Traders post orders (UTxOs at `order(S)`, tagged `S`). A solver builds a settlement: spends the pool (`PoolSettle`) + all chosen orders (`Settle`) + a withdraw-0 for `S`; `clearing.run` pins every owner payout, every partial-fill remainder, and the pool output to exact values, enforces uniform price, per-order floor, deadlines, and the injective O(N) order→output binding. Terminal: a pre-seed pool may be torn down by its creator (`ClosePool`, burns NFT + LP).

**Major assets:** per-pool one-shot **NFT** (`nft_name = "NFT"`) and **LP** token (`lp_name = "LP"`), both under the pool's `pool_mint` policy; plus the two traded assets (`asset_a`, `asset_b`, either may be ADA).

**Expected tx shapes:** see §5.

**Off-chain assumptions:** solvers/batchers are **untrusted** (only verified); the off-chain builder is trusted to (a) place pool/order/lp-intent UTxOs at the correct addresses with the correct stake tag, and (b) set `owner` to a verification-key hash. These are the off-chain enforcers tracked in §4/§11.

**User roles:** trader (posts orders), liquidity provider (deposits/withdraws), pool creator (seeds + may close pre-seed), solver/batcher (untrusted).

**Admin roles:** none — there is no admin, upgrade, pause, or emergency key. `S` is immortal and undelegatable.

**Hyperstructure assumptions:** the protocol is admin-free and immutable by design (see §9); there are no always-true escape hatches (every validator ends `else -> fail`).

### 3.8 Builder-Bypass Question

**Is the validator safe if a malicious user bypasses any official off-chain builder? — Partially.** Against handcrafted transactions the core settlement is robust: every owner payout, remainder, and the (S-tagged) pool output is value-pinned, `mint == 0` is asserted, the order→output binding is injective by `OutputReference`, and the pool's `k` is enforced — so a handcrafted solver can extract only the posted tips. pub fn pool_settle(
```aiken
  tx: Transaction,
  utxo: OutputReference,
  d: PoolDatum,
  s: Credential,
) -> Bool {
  expect utils.withdrawal_present(tx, s)
  expect Some(own) = list.find(tx.inputs, fn(i) { i.output_reference == utxo })
  // the spent input must itself be the NFT-bearing pool (parity with lp_action,
  // which checks this too). The settlement anchor also enforces a single
  // NFT-bearing pool input, but the pool owns its own continuity (§5.4).
  expect utils.asset_qty(own.output.value, d.nft) == 1
  expect [out] = list.filter(
    tx.outputs,
    fn(o) {
      o.address == own.output.address && utils.asset_qty(o.value, d.nft) == 1
    },
  )
  // pool identity/params unchanged across the settlement (nft, pair, fee) — the
  // settlement anchor also pins this, but the pool owns its own continuity
  expect out.datum == own.output.datum
```

```aiken
  // with per-order/per-remainder full-value pins, `mint == 0`, and ledger value
  // conservation, the solver can take only the proportional tips — no separate
  // global-conservation pass needed.
  let pool_val_exp = pool_in.output.value
    |> assets.add(r.asset_a.policy, r.asset_a.name, net_a)
    |> assets.add(r.asset_b.policy, r.asset_b.name, net_b)
  expect pool_out.value == pool_val_exp
  // pool identity/params (and curve state) can't be mutated mid-settlement
  expect pool_out.datum == pool_in.output.datum
```

**What It Is:**
`pool_settle` (the `PoolSettle` path) pins three things on the recreated pool output — the NFT (`asset_qty(out.value, d.nft) == 1`), the address (`o.address == own.output.address`), and the datum (`out.datum == own.output.datum`) — plus the reserve-side `k`-check and price pin. It never pins the **LP token held in the pool** and never asserts the spent pool is tagged with `S`. Held-LP integrity is delegated to the settlement anchor, whose full-value pin (`pool_out.value == pool_in.value` shifted only on `asset_a`/`asset_b`, clearing.ak:379-382) *does* preserve held LP — but the anchor only enumerates and pins pools that are **S-tagged** (`is_tagged` filters by `stake_credential == Some(Inline(S))`, clearing.ak:306-309, 342-352). The code comment at clearing.ak:372-378 states the intent precisely ("preserves its … held LP … so a solver can't strip the pool's LP (then drain via `LpAction`)"). Note the contrast with `order_settle`, which self-enforces `is_tagged(own.output, s)` (spend.ak:68) to "close the input-smuggle path"; `pool_settle` checks only `withdrawal_present(tx, s)` (a global tx property) and omits the per-pool tag check.

**Why It Is Bad — Cardano Semantic Cited:**
On Cardano a spend validator runs **independently on every script input with the same `Transaction` view**, and there is no rule that all UTxOs sharing one payment credential share a stake credential. `mint.create` finds the pool output by `(NFT, LP)` presence only and never checks its address or stake credential (mint.ak:30-39; the "off-chain builder is still responsible" comment, mint.ak:60-67). So a pool can be created at the **`pool(S)` payment credential** (so `pool.ak` runs) but with a **non-S stake credential**. Such a pool is spendable via `PoolSettle`, yet is invisible to `clearing.run` (which enumerates by the `S` tag). Two pools with distinct NFTs are distinct UTxOs and can be spent in one tx; nothing forces the `PoolSettle`'d pool to be the one the anchor enumerated. Held LP held in a continuing output is a protocol asset — "required-in / not-required-out" lets it walk free, exactly the asymmetry in `ctf/bank_07_no_mint_no_problem.md`.

**Attack Scenario:**
- **Setup:** attacker creates pool `Q` via `pool_mint.Create` at address `{payment = Script(pool(S)), stake = <non-S>}` (a distinct seed ⇒ distinct NFT). `Q` is a valid-looking pool (one-shot NFT, well-formed `PoolDatum`, at the canonical pool script address). Victims deposit liquidity into `Q` via `pool.LpAction` or `lp_intent.Fulfill` — both bind the pool by NFT/address and never check the `S` tag, so victims have no on-chain signal `Q` is mis-tagged. `Q` accrues reserves; held LP ≈ `total_lp − circulating`.
- **Extraction tx:** inputs = `Q` (non-S) spent via `PoolSettle`, plus any real **S-tagged** pool `A` spent via `PoolSettle` with a `SettlementRedeemer` for `A` and **zero orders**; a withdraw-0 for `S` (anyone may add it). Outputs: `A` unchanged (clearing pins it: `net = 0`); `Q'` at `Q`'s address with reserves + datum + NFT **unchanged** but **held LP = 0**; an attacker wallet output receiving the extracted LP.
  - `clearing.run`: `tagged_inputs = [A]` (non-S `Q` excluded), `expect [pool_in] = [A]` ✓, zero orders ⇒ `process` returns `(0,0)`, `pool_out(A) == A` ✓, `mint == 0` ✓ → passes.
  - `pool.ak` on `A`: `withdrawal_present(S)` ✓, `k` unchanged ✓ → passes.
  - `pool.ak` on `Q`: `withdrawal_present(S)` ✓, NFT continuity ✓, datum unchanged ✓, reserves unchanged ⇒ `k_ok` at equality ✓, no residual ⇒ `pin_ok = True` ✓. Held LP unconstrained → `Q'.held_LP = 0`, the rest goes to the attacker. Passes.
- **Redemption tx (separate):** attacker spends an `lp_intent`/`lp_action` `LpWithdraw` returning the extracted LP; `released = res_in · l / circ_in`. With `held ≈ total_lp`, the attacker holds ≈ all circulating LP and withdraws ≈ all of `Q`'s reserves. **End state:** victim LPs are diluted to near-zero backing; the attacker has drained the pool's reserves.

**Proof / Evidence:**
- Quoted code above is the primary evidence: `pool_settle` pins NFT/address/datum/reserves but not held LP, and uses only `withdrawal_present` where `order_settle` additionally uses `is_tagged`.

The reachability lens confirmed `lp_action`/`fulfill` bind pools by NFT/address only (no `S`-tag check), so victims can deposit into `Q`.
- Cross-reference: [attacks/value.md:14-71](../../../attacks/value.md#L14-L71) (value not preserved on continuing output), [ctf/bank_07_no_mint_no_problem.md:13-26](../../../ctf/bank_07_no_mint_no_problem.md#L13-L26) (token required in input, not in output → diverted from the output side).
- PoC test sketch (fails before fix, passes after):

```aiken

  // attacker output: same addr / datum / reserves / NFT but held_lp = 0
```

```aiken

```

**Severity:** Low

**Confidence:** Suspected

**Status:** Design Tradeoff

**CWC ID:** [CWC-018](../../../taxonomy.md) (insufficient access control / unenforceable creation invariant; lock aspect [CWC-028](../../../taxonomy.md))

**Root Cause:** `owner-vk-off-chain-only`

**Component:** order validator / lp_intent validator (reclaim path)

**Location:**

- [lib/shaswap/spend.ak:72-75](../../../contracts/shaswap/lib/shaswap/spend.ak#L72-L75)
- [lib/shaswap/lp_intent.ak:240-242](../../../contracts/shaswap/lib/shaswap/lp_intent.ak#L240-L242)

**Quoted Code (`lib/shaswap/spend.ak:72-75`):**

```aiken
pub fn order_reclaim(owner: Credential, tx: Transaction) -> Bool {
  expect VerificationKey(vkh) = owner
  list.has(tx.extra_signatories, vkh)
}
```

**What It Is:**
Reclaim (the non-custodial escape) requires `owner` to be a `VerificationKey` credential — `expect VerificationKey(vkh) = owner` crashes the validator otherwise. An order or LP-intent whose `owner` is a `Script` credential is therefore settleable/fulfillable (the payout lands at the script address fine) but **never reclaimable**. If such a UTxO is never settled, its funds are locked. The README documents this exactly (L-01) and states the off-chain builder **must** set `owner` to the wallet's payment key hash.

**Why It Is Bad — Cardano Semantic Cited:**
Spend validators **do not run when a UTxO is created**, only when spent — so neither `order` nor `pool_mint` can reject a `Script`-credential `owner` at creation time. The invariant "`owner` is a verification key" is thus unenforceable on-chain at the only moment it could be checked, and is delegated to the off-chain builder. This is a documented off-chain enforcement (Phase 5d auto-finding).

**Attack Scenario:**
No third-party attack: the only party who can set a `Script` owner is the UTxO's own creator, and the only victim is that same creator (self-grief). A user (or a buggy builder) who posts an order with a `Script` `owner` that no solver ever settles cannot reclaim it → funds locked. Recorded because the lock is permanent and the enforcement lives entirely off-chain.

**Proof / Evidence:**
- Quoted code: the `expect VerificationKey` gate on reclaim, with no symmetric rejection at settle/create.
- Cross-reference: [attacks/state.md:169-219](../../../attacks/state.md#L169-L219) (lifecycle: invariants validated only on later spend, not at creation), [ctf/bank_04_lifecycle.md](../../../ctf/bank_04_lifecycle.md) (validators don't run on UTxO creation).

**How To Fix:**
This cannot be enforced on-chain at creation. Mitigations, in order of preference: (a) keep the documented builder requirement and add a builder-side assertion + a UI guard that refuses `Script` owners; (b) document it as an accepted v1 limitation (already done in README). No code change is safe to *force* here without breaking the legitimate `Script`-owner-can-still-be-settled path.

**Tests To Add:**

- Negative
  - [ ] Off-chain builder test: reject constructing an order whose `owner` is a `Script` credential.
- Positive
  - [ ] On-chain test: a `Script`-owner order is still settleable (documents the asymmetry).

**Additional Notes:**
- Documented non-verbal enforcer (README:30-37) → per the §4 Documented-Trust-Model table, demote exactly one tier and set Status = **Design Tradeoff**. Class default for a lock-forever footgun would be Medium; demoted to **Low**.
- `(borderline Low / Informational because the lock is fully self-inflicted and the affected order remains settleable)` — kept at Low because the loss, when it occurs, is permanent.

**What It Is:**

**Attack Scenario:**
N/A — no profitable attack. Recorded for the verify-don't-trust symmetry with `fulfill` and to make un-settleable configs fail with an explicit message rather than via an emergent bound.

**Severity:** Informational

**Confidence:** Confirmed

**Status:** Not Exploitable As Written

**Quoted Code (`lib/shaswap/spend.ak:190-202`):**

```aiken
fn lp_at(outputs: List<Output>, cred: Credential, lp: AssetId) -> Int {
  list.foldl(
    outputs,
    0,
    fn(o, acc) {
      if o.address.payment_credential == cred {
        acc + utils.asset_qty(o.value, lp)
      } else {
        acc
      }
    },
  )
}
```

**What It Is:**
On the first deposit, `lp_action` requires `lp_at(tx.outputs, Script(d.nft.policy), lp) >= min_liq` — i.e. at least `min_liq` LP must sit at outputs whose **payment credential** is the mint-policy script. `lp_at` matches the payment credential only; the stake credential and `reference_script` of the lock output are unconstrained.

**Why It Is Bad — Cardano Semantic Cited:**
Cardano addresses are `(payment_credential, stake_credential)`, and the §11 perimeter walk flags any continuing-output match that pins payment but not stake (CWC-018) or reference-script (CWC-021). Here, however, the matched credential is `Script(d.nft.policy)` — the `pool_mint` policy, which has **no spend handler** (`else -> fail`), so the lock output is **permanently unspendable** regardless of its stake credential or reference script. The "hijack" would only redirect staking rewards on the lock UTxO's own min-ADA dust (set by the first depositor, on their own contribution), and any attached reference script would bloat a single dust UTxO that nobody re-spends. There is no value-pooling continuing output here and no third-party victim.

**Attack Scenario:**
None with material impact. The first depositor could set the lock output's stake credential to their own and earn staking rewards on ~`min-ADA` of dust they themselves locked, forever; or attach a reference script that bloats only that one unspendable UTxO. Neither affects other LPs, the reserves, or the locked LP (which is unspendable). Recorded to complete the §11 perimeter walk.

**Proof / Evidence:**
- Quoted code: `lp_at` matches `o.address.payment_credential == cred` only.
- Cross-reference: [attacks/authentication.md:434-543](../../../attacks/authentication.md#L434-L543) (§11 Address-Perimeter Walk), [taxonomy.md](../../../taxonomy.md) (CWC-018 / CWC-021).

**How To Fix:**
No security fix required (the target address is unspendable). If desired for cleanliness, the first-deposit rule could additionally require the lock output's stake credential be `None` and its reference script be `None`; this is cosmetic given the unspendable payment credential.

**Tests To Add:**

- [ ] (Optional) Assert the `min_liq`-lock output carries `stake_credential: None` and `reference_script: None` — documents intent; not a security boundary.

Contrast with the protocol's genuine continuing-output helpers `is_protocol_output` and `is_payout_output`, which use **full-address equality** and reject reference scripts (see §13.2) — the perimeter elsewhere is clean.

### O-01 `pool_settle` re-filters all tx inputs to recompute `n_orders`

**Severity:** Optimization

**Confidence:** Likely

**Status:** Optimization Opportunity

**CWC ID:** [CWC-016](../../../taxonomy.md) (resource use; optimization, not a vulnerability)

**Root Cause:** `n-orders-refilter`

**Component:** pool validator (`pool_settle` price pin)

**Location:**

- [lib/shaswap/spend.ak:148-150](../../../contracts/shaswap/lib/shaswap/spend.ak#L148-L150)

**Quoted Code (`lib/shaswap/spend.ak:148-150`):**

```aiken
  let n_orders = list.length(
    list.filter(tx.inputs, fn(i) { utils.is_tagged(i.output, s) }),
  ) - 1
```

**What It Is:**
`pool_settle` computes the dust-band `eps = n_orders` by filtering **all** transaction inputs for the `S` tag and taking the length. In the same transaction, `clearing.run` already performs the identical `is_tagged` filter over `tx.inputs` (clearing.ak:306-309). The two run in separate scripts (the pool spend and the settlement withdraw), so the work cannot be shared directly, but `pool_settle` re-traverses the full input list a second time solely to obtain a count.

**Why It Is Bad — Cardano Semantic Cited:**
Pure cost: `list.filter` + `list.length` is an O(inputs) traversal (allocating an intermediate list) executed inside the per-pool validator on every settlement. For large batches (the README bounds ~40–50 orders/settlement) this is a measurable, repeated traversal. No security impact — `eps`'s correctness does not depend on the traversal style.

**Attack Scenario:**
N/A — optimization.

**Proof / Evidence:**
- Quoted code; the duplicate `is_tagged` filter in `clearing.run` at clearing.ak:306-309.
- Cross-reference: [optimizations/aiken_optimization_guide.md](../../../optimizations/aiken_optimization_guide.md) (#12 avoid re-traversals; #16 fold-with-count), [optimizations/stdlib_red_flags.md](../../../optimizations/stdlib_red_flags.md) (`list.count` / `list.length(list.filter …)` row).

**How To Fix:**
Replace `list.length(list.filter(...))` with a single counting fold (`list.foldl(tx.inputs, 0, fn(i, n) { if is_tagged(i.output, s) { n + 1 } else { n } }) - 1`), avoiding the intermediate list allocation. Expected benefit: one fewer full-list allocation + traversal per settlement (script CPU/mem; magnitude scales with input count — measure with the existing `pool__pool_settle` bench before/after). Risk: low (semantically identical count).

**Tests To Add:**

- Benchmark
  - [ ] Re-run `bench pool__pool_settle` before/after the fold rewrite at low-N / mid-N / high-N input counts and record the delta.

**Additional Notes:**
Baseline benchmarks **exist** (13 `bench` blocks, incl. `pool__pool_settle`), so the before/after delta is directly measurable. Filed as the single genuine optimization opportunity; the other scanned candidates (bounded `assets.flatten`/`restricted_to` in `mint`, `list.zip` in `clearing`, the explicit `>= 0` reserve guards) are acceptable or correctness-required and are recorded in §19.

**Knowledge References:**

1. [optimizations/aiken_optimization_guide.md](../../../optimizations/aiken_optimization_guide.md) — #12 (avoid re-traversals) / #16 (tail-recursive count fold).
2. [optimizations/stdlib_red_flags.md](../../../optimizations/stdlib_red_flags.md) — `list.count` / `list.length(list.filter …)` red-flag row.

## 20. Final Recommendations

### 20.0 Coordinated Fixes

### Must Fix Before Mainnet

- **H-01** — add the `is_tagged(own.output, s)` self-check (and/or a held-LP pin) to `pool_settle`, so a non-S pool cannot be spent via `PoolSettle` and have its held LP extracted. This also removes the on-chain reliance on the off-chain pool-placement invariant.

### Should Fix Before Mainnet

- **L-01** — keep the documented `owner = VK` builder requirement; add a builder/UI guard rejecting `Script` owners (cannot be enforced at on-chain creation).

### Nice To Have

- **I-02** — add `expect order.tip >= 0` / `expect order.sell_amount >= 1` in `check_one` for parity with `fulfill`.
- **I-03** — (cosmetic) pin the `min_liq`-lock output's stake credential / reference script to `None`.

### Optimization Backlog

- **O-01** — replace `list.length(list.filter(...))` for `n_orders` with a counting fold; measure via the existing `pool__pool_settle` bench.
