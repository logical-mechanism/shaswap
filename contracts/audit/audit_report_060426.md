- **Top three concerns:**
  1. **H-01** — the partial-fill remainder datum is solver-authored and `consume_remainder` pins every field *except* `pool_nft`, so a malicious solver can redirect the unsold portion of any `partial`-eligible order to an attacker-controlled pool and rug it on a later settlement (reopens the C-02 bought-asset substitution for remainders).
  2. **M-01** — the standalone `pool.LpAction` path does **not** pin the pool output's full value (only NFT + reserves + held LP), unlike the settlement and `lp_intent` paths; an attacker can pile dust native-assets into the shared pool UTXO via no-op LP actions, bloating it toward `maxValSize` and degrading/DoS-ing settlements.
  3. **L-01 / I-06** — the new `lp_intent` subsystem repeats the prior `order` "owner not constrained to a verification-key credential" creation gap (Script-owner UTxO is settle-able but never reclaimable), and the whole suite tests *library functions* — never a `validator` entrypoint — so redeemer dispatch, the `pool.ak` mutual-exclusion guard, the `expect Some(d)=datum` path, and every `else -> fail` arm are unexercised.
- **Production / experimental assessment:** The on-chain security of the *settlement / conservation / LP-backing / perimeter* core is **production-grade and well-tested**. The protocol is **Not Ready** for mainnet only because of H-01 (a genuine loss-of-funds path for partial orders) plus the M-01 griefing vector; both are narrowly-scoped code fixes (pin one more datum field; pin the full pool value on the standalone path). With H-01/M-01 fixed and L-01/I-06 addressed, this reaches Mainnet-ready.
- **Readable-for-a-non-auditor summary:** ShaSwap lets untrusted "solvers" batch trades and settle them in one transaction; the contracts only *check* the solver's work. The checking is thorough — solvers can only keep the tips traders posted, and cannot steal deposits or pool reserves. The audit found one real hole: when an order is only *partially* filled, the leftover piece can be silently re-pointed at a fake pool by the solver and later cashed out for worthless tokens. That, plus a way to clog a pool with junk tokens, must be fixed before real money is used.

## 3. Contract Overview

ShaSwap is a fully-decentralized, non-custodial, MEV-resistant **batch-auction DEX**. Untrusted solvers compute a uniform-price clearing for a batch of orders off-chain; the validators only *verify* it. There is no admin, operator, batcher allow-list, upgrade, or pause.

**Validators / policies:**

- **`settlement`** — the immutable trust anchor. An **unparameterised withdraw-0 staking script**: it learns its own credential `S` at run time as the withdraw account, enumerates every input stake-tagged with `S`, classifies each by datum shape (parses-as-`OrderDatum` ⇒ order; the sole non-order ⇒ the pool), and enforces the curve-agnostic batch rules — conservation (exact value-pins), uniform price, per-order floor, injective O(N) order→output binding, deadlines, and partial-fill remainders ([clearing.run, clearing.ak:263-358](../../contracts/shaswap/lib/shaswap/clearing.ak#L263-L358)). Its `publish` handler permits *only* registration of `S` ([allow_registration, clearing.ak:48-53](../../contracts/shaswap/lib/shaswap/clearing.ak#L48-L53)) — never de-registration or delegation — keeping the anchor immortal and undelegatable.
- **`order(S)`** — user order validator, parameterised by `S`. `Settle` defers to the settlement anchor and self-enforces its own `S` tag ([spend.order_settle, spend.ak:39-46](../../contracts/shaswap/lib/shaswap/spend.ak#L39-L46)); `Reclaim` is owner-signature-only ([spend.order_reclaim, spend.ak:49-52](../../contracts/shaswap/lib/shaswap/spend.ak#L49-L52)).
- **`pool(S)`** — constant-product pool, parameterised by `S`. Owns its curve: `PoolSettle` checks `k_after ≥ k_before` with a static fee, `LpAction` runs the value-derived LP deposit/withdraw under a mutual-exclusion guard, `ClosePool` tears down an unseeded pool ([pool.ak:14-39](../../contracts/shaswap/validators/pool.ak#L14-L39); [spend.ak:54-202](../../contracts/shaswap/lib/shaswap/spend.ak#L54-L202)).
- **`pool_mint(seed)`** — one-shot pool-creation/closure minting policy, parameterised by a seed `OutputReference` (so the pool NFT is unique). `Create` mints `{NFT:1, LP:total_lp}` into a validated pool output; `Close` is burn-only ([mint.ak:18-72](../../contracts/shaswap/lib/shaswap/mint.ak#L18-L72)).
- **`lp_intent(S)`** — batcher-fulfilled LP deposit/withdraw *intent* (the newest subsystem). `Fulfill` pins the owner payout exactly and asserts the settlement withdraw-0 for `S` is **absent** (forcing the coupled pool spend to be `LpAction`, where per-share backing runs); `ReclaimLp` is owner-signature-only ([lp_intent.ak:83-221](../../contracts/shaswap/lib/shaswap/lp_intent.ak#L83-L221)).

**Protocol flow:** *create* (`pool_mint Create` → seeded pool at `pool(S)` with NFT+LP) → *trade* (users post `order(S)` UTXOs tagged `S`; a solver settles one pool + a batch of orders via the `S` withdraw-0) / *provide liquidity* (`pool.LpAction` directly, or `lp_intent(S).Fulfill` via a batcher) → *terminal* (`ClosePool` only while unseeded; post-seed pools are immortal because `min_liq` LP is permanently locked at the unspendable mint-policy address).

**Major assets:** per-pool NFT (`#"4e4654"` "NFT") and LP token (`#"4c50"` "LP"), both under the pool's `pool_mint(seed)` policy; the traded pair `(asset_a, asset_b)` (either side may be ADA), guaranteed external to the pool's own policy.

**User roles:** order owner (VK), LP-intent owner (VK), pool creator (VK, pre-seed teardown only), liquidity provider (permissionless `LpAction`). **Admin roles:** none (explicit hyperstructure claim). **Off-chain assumptions:** solver/batcher are *untrusted*; the off-chain builder is responsible only for *creation-time* placement (pool at the `pool(S)` address with `pool_min_ada`; well-formed owner credentials) — see L-03, §11.

### 3.8 Builder-Bypass Question

**Is the validator safe if a malicious user bypasses any official off-chain builder? — Partially.** The protocol is explicitly designed for adversarial, handcrafted transactions: solvers and batchers are *untrusted* and there is no privileged builder. The core value movements are pinned on-chain — owner payouts (`bound.value == owner_val`, [clearing.ak:213](../../contracts/shaswap/lib/shaswap/clearing.ak#L213)), the pool residual (`pool_out.value == pool_val_exp`, [clearing.ak:352](../../contracts/shaswap/lib/shaswap/clearing.ak#L352)), `mint == 0` ([clearing.ak:340](../../contracts/shaswap/lib/shaswap/clearing.ak#L340)) — so a handcrafted settlement cannot steal a *fully-filled* trader's funds or strip pool reserves, and the address perimeter is fully pinned (no stake-hijack / no ref-script bloat, §5f). **The "partially" is H-01 and M-01:** a handcrafted *partial* settlement can re-point a remainder at an attacker pool (H-01), and a handcrafted standalone `LpAction` can bloat the shared pool (M-01). So bypass-resistance holds for the full-fill trade and reserve-theft surface, but **not** for the partial-fill remainder rollover or the standalone LP value-pin.

## 6. Ranking System

- **Severity tiers:** Critical (direct theft / lock / unauthorized mint / total bypass), High (major invariant break / realistic loss), Medium (incorrect behaviour / narrow loss / realistic DoS / unsafe off-chain reliance), Low (narrow edge / brittle / security-adjacent smell), Informational (docs / tests / naming), Optimization (cost only, never a security tradeoff).

- **Status values:** Open, Needs Verification, Not Exploitable As Written, Design Tradeoff, Intentional Hyperstructure Behavior, Optimization Opportunity.
- **Production-readiness rubric (§16):** *Mainnet-ready* (Critical/High = 0; redeemers covered with negatives; hyperstructure paths classified) / *Needs Work* (≥1 High; or coverage gaps) / *Not Ready* (any Critical; or tests largely absent; or hyperstructure Dangerous) / *Research-Experimental*. ## 8. Detailed Findings

### High

### [H-01] Partial-fill remainder rollover does not pin `pool_nft` → a solver can redirect the unsold portion of any partial order to an attacker-controlled pool and rug it

**Severity:** High

**Confidence:** Confirmed

**Status:** Open

**CWC ID:** CWC-010

**Root Cause:** `remainder-datum-pool-nft-unpinned`

**Component:** settlement / `clearing.consume_remainder`

**Location:**
- [clearing.ak:94-124](../../contracts/shaswap/lib/shaswap/clearing.ak#L94-L124)
- [clearing.ak:140-144](../../contracts/shaswap/lib/shaswap/clearing.ak#L140-L144) (the per-order binding it should mirror)
- [clearing.ak:215-227](../../contracts/shaswap/lib/shaswap/clearing.ak#L215-L227) (where the remainder is constructed and consumed)

**Quoted Code (`clearing.ak:110-123`):**
```aiken
  expect InlineDatum(rd) = rem.datum
  expect ro: OrderDatum = rd
  expect ro.owner == order.owner
  // the remainder is a continuing order that will itself pay out later, so it must
  // carry the SAME payout stake credential (the solver can't swap it on the rollover)
  expect ro.owner_stake == order.owner_stake
  expect ro.sell_a == order.sell_a
  expect ro.sell_amount == new_sell
  expect ro.tip == tip_rem
  expect !ro.partial
  expect ro.deadline == order.deadline
  // limit price preserved or improved (never fills worse than the original)
  expect ro.limit * order.sell_amount >= order.limit * new_sell
  rest
```

**What It Is:**
`consume_remainder` validates the solver-authored remainder `OrderDatum` field-by-field against the original order — `owner`, `owner_stake`, `sell_a`, `sell_amount`, `tip`, `partial`, `deadline`, and the limit *price* ratio — but it never asserts `ro.pool_nft == order.pool_nft`. The remainder's `pool_nft` field is therefore entirely solver-chosen. Because the original order's whole defense against bought-asset substitution (the prior C-01/C-02 fix) is the chain "`order.pool_nft == r.pool_nft`" → "`r.pool_nft == spent PoolDatum.nft`" → "the pair is the pool's real `(asset_a, asset_b)`", a remainder that carries a *different* `pool_nft` is no longer bound to the pool the owner consented to.

**Why It Is Bad — Cardano Semantic Cited:**
Spend validators do not run on UTXO creation; the remainder is a *continuing order UTXO* created inside the settlement and its datum is supplied by the (untrusted) solver. On Cardano, asset identity is `(policy_id, asset_name)` and the per-order floor `limit` is a bare `Int` (a count of the *bought* asset, whose identity is resolved only at settlement time from the spent pool's pair). When the remainder is later settled against a different pool, [clearing.ak:144](../../contracts/shaswap/lib/shaswap/clearing.ak#L144) `expect order.pool_nft == r.pool_nft` is satisfied by the *remainder's* solver-chosen `pool_nft`, so the floor is checked in units of the *new* pool's `asset_b`. The floor count is met with a worthless token — the integer `limit` carries no asset identity.

**Attack Scenario:**
- **Setup.** Attacker creates a legitimate-looking pool `Q` via `pool_mint(seed_Q)` with `asset_a = X` (the order's sold asset) and `asset_b = Z` (a worthless attacker token), seeds it minimally.
- **Step 1 (partial fill against the honest pool `P`).** Honest owner posts order `O`: sell `X`, buy `P.asset_b`, `pool_nft = P`, `partial = True`, large `sell_amount`. Attacker (acting as solver) settles `O` against `P` with fill `f = 1`. The first settlement is valid: `O.pool_nft == P` holds, and `consume_remainder` accepts a remainder `R` whose datum copies every field **except** `pool_nft`, which the attacker sets to `Q`. `R` holds `sell_amount − 1` units of `X` at the order's own `S`-tagged address.
- **Step 2 (rug against `Q`).** Attacker settles `R` against pool `Q` (`r.pool_nft = Q`, the spent pool input is `Q`). `R.pool_nft == Q` holds; `R` sells its `X` and the floor `new_sell·price_num ≥ R.limit·price_den` is satisfied by paying the owner `R.limit` units of the worthless `Z`. The owner's `X` flows into attacker-controlled pool `Q`.
- **End-state:** the attacker captures ~the entire unsold balance (the solver can pick `f = 1`) of any `partial`-eligible order for the cost of a worthless mint. The owner receives a dust amount of a worthless token. This is principal theft of the remainder portion, requiring an adversarial pool + solver setup → High.

**Proof / Evidence:**
- Quoted code above — `pool_nft` is absent from the remainder field checks; grep confirms `pool_nft` appears in `clearing.ak` only at lines 144, 290, 300, 309-310, 319 (never inside `consume_remainder`, 94-124).
- No test covers it: `partial_remainder_wrong_stake`, `partial_remainder_shorted`, `partial_remainder_bad_limit` exist ([clearing_test.ak:735-758, 1361](../../contracts/shaswap/lib/shaswap/clearing_test.ak#L735-L758)) but there is **no** `partial_remainder_wrong_pool_nft`.
- PoC test sketch (fails before fix, passes after):
```aiken
test partial_remainder_wrong_pool_nft() fail {
  // build a valid partial settlement against pool P, but author the remainder
  // datum with pool_nft = Q (an attacker pool's NFT) and every other field copied.
  // Before the fix this passes (bug); after adding `expect ro.pool_nft == order.pool_nft`
  // it must FAIL.
  let tx = partial_settlement_with_remainder_pool_nft(attacker_pool_nft)
  clearing.run(s(), redeemer_for(tx), tx)
}
```

**How To Fix:**
Add one line to `consume_remainder`, mirroring [clearing.ak:144](../../contracts/shaswap/lib/shaswap/clearing.ak#L144):
```aiken
  expect ro.pool_nft == order.pool_nft
```
This pins the remainder to the same pool the owner originally consented to, restoring the C-02 binding across the rollover. (`limit`, already constrained as a *price*, then again carries the original pool's real asset identity.)

**Tests To Add:**
- Negative
  - [ ] Rejects a remainder whose `pool_nft` differs from the original order's (the PoC above)
  - [ ] Rejects a remainder whose `pool_nft` is a real-but-different live pool's NFT
- Property
  - [ ] Fuzz the remainder `pool_nft` over the policy/name space; every value `≠ order.pool_nft` must fail

**Additional Notes:**
Only `partial`-eligible orders are exposed, and only the *unsold* portion; a `partial == False` order produces no remainder and is unaffected. Borderline High/Critical (the solver can choose `f = 1` to expose almost the whole order); per the value-leak/principal-theft rubric "principal theft requiring an adversarial setup → High by default", filed as High. This is the single most consequential gap and the clearest case of the adjacent-code heuristic: the C-02 fix hardened the *primary* order binding but the *remainder rollover* — a parallel datum-authoring site — was missed.

### Medium

### [M-01] Standalone `LpAction` does not pin the pool output's full value → native-asset bloat DoS of the shared pool UTXO

**Severity:** Medium

**Confidence:** Likely

**Status:** Open

**CWC ID:** CWC-016

**Root Cause:** `lp-action-value-not-fully-pinned`

**Component:** pool / `spend.lp_action`

**Location:**
- [spend.ak:151-202](../../contracts/shaswap/lib/shaswap/spend.ak#L151-L202)
- [spend.ak:159-166](../../contracts/shaswap/lib/shaswap/spend.ak#L159-L166) (the pool-output match and its only value constraints)

**Quoted Code (`spend.ak:159-185`):**
```aiken
  expect [out] = list.filter(
    tx.outputs,
    fn(o) { o.address == in_addr && utils.asset_qty(o.value, d.nft) == 1 },
  )
  // pool identity/params unchanged (nft, token, fee); no attached reference script
  expect out.datum == own.output.datum
  expect out.reference_script == None
  ...
  let res_a_out = reserve_of(out.value, d.asset_a)
  let res_b_out = reserve_of(out.value, d.asset_b)
  ...
  let held_out = utils.asset_qty(out.value, lp)
```

**What It Is:**
On the standalone (no-settlement) `LpAction` path, the recreated pool output is matched only by full address + `asset_qty(NFT) == 1`, and the only further value constraints read individual quantities (`reserve_of` for `asset_a`/`asset_b`, `asset_qty` for LP). There is **no** `out.value == <expected full value>` pin. Every *other* policy's tokens in the pool output are unconstrained. By contrast, the settlement path pins the pool value exactly (`pool_out.value == pool_val_exp`, [clearing.ak:352](../../contracts/shaswap/lib/shaswap/clearing.ak#L352)) and the `lp_intent` path pins it exactly ([lp_intent.ak:166](../../contracts/shaswap/lib/shaswap/lp_intent.ak#L166), [lp_intent.ak:201](../../contracts/shaswap/lib/shaswap/lp_intent.ak#L201) — whose own comment notes the intent path is *stricter* than "the frozen direct `LpAction` path which leaves the pool's incidentals unpinned").

**Why It Is Bad — Cardano Semantic Cited:**
`LpAction` requires no signature (liquidity provision is permissionless) and the per-share backing invariants hold with equality for an unchanged reserve/share state, so a "no-op" `LpAction` — same NFT, same reserves, same held LP, same datum, plus arbitrary extra native assets — passes. Cardano caps a single output's value at the protocol `maxValueSize`; an attacker can repeatedly add distinct dust tokens (funding the growing min-ADA) until the pool output approaches that cap. Thereafter every *settlement* must reproduce the pool value exactly (`pool_out.value == pool_in.value + residual`, [clearing.ak:349-352](../../contracts/shaswap/lib/shaswap/clearing.ak#L349-L352)), so the bloat persists and inflates the size/cost of every batch — a denial-of-service on the single shared pool UTXO that holds all LPs' liquidity.

**Attack Scenario:**
- inputs: the pool UTXO (spent via `LpAction`) + an attacker wallet input carrying many distinct dust tokens.
- outputs: the recreated pool UTXO at the same address, same NFT/reserves/held/datum, **plus** the dust tokens; attacker change.
- mint: `assets.is_zero(tx.mint)` (no mint needed).
- signers: none required.
- end-state: pool output grows by the dust; repeat until near `maxValueSize`. Settlements against this pool become large/expensive or infeasible; LPs' withdrawals are degraded until someone performs a cleanup `LpAction` that drops the dust.

**Proof / Evidence:**
- Quoted code — the pool output's full value is never pinned on this path; the developers' own comment at [lp_intent.ak:157-161](../../contracts/shaswap/lib/shaswap/lp_intent.ak#L157-L161) confirms the asymmetry ("STRICTER than the frozen direct `LpAction` path … leaves the pool's incidentals unpinned").
- The per-share backing checks ([spend.ak:198-201](../../contracts/shaswap/lib/shaswap/spend.ak#L198-L201)) constrain only `asset_a`/`asset_b`/held — never a foreign policy's quantity.

**How To Fix:**
Pin the pool output's full value on the standalone path, mirroring the settlement/intent paths. Reconstruct the expected value from the input shifted by the LP/reserve deltas and assert equality:
```aiken
  let pool_exp =
    own.output.value
      |> assets.add(d.asset_a.policy, d.asset_a.name, res_a_out - res_a_in)
      |> assets.add(d.asset_b.policy, d.asset_b.name, res_b_out - res_b_in)
      |> assets.add(lp.policy, lp.name, held_out - held_in)
  expect out.value == pool_exp
```
This is exactly the discipline already used in `clearing.ak` and `lp_intent.ak`; adopting it makes all three pool-mutation paths uniform and closes both M-01 and L-02. (Coordinated fix — see §20.0.)

**Tests To Add:**
- Negative
  - [ ] Rejects an `LpAction` whose pool output carries an extra foreign-policy asset
  - [ ] Rejects an `LpAction` that mutates the pool's overhead lovelace (token/token pool — see L-02)
- Property
  - [ ] Fuzz an extra `(policy, name, qty)` into the pool output; must fail for any non-`{asset_a,asset_b,nft,lp}` asset

**Additional Notes:**
Borderline Medium/Low: the bloat is bounded by `maxValueSize` and is recoverable by a cleanup `LpAction` that drops the dust, and the attacker must fund the min-ADA — so it is griefing/DoS of a shared resource, not theft. Filed Medium because it degrades a pool holding *other* users' liquidity and forces remediation; pick-the-lower-tier guidance would allow Low, but the shared-resource impact justifies Medium. Reserves and shares themselves remain protected by the per-share backing invariant, so no LP principal is *stolen* via this path.

**Knowledge References:**
- [attacks/dos.md](../../attacks/dos.md) (token-dust / value-bloat DoS)
- [attacks/value.md](../../attacks/value.md) (value not fully preserved on a continuing output)
- [ctf/10_king_of_cardano.md:79-95](../../ctf/10_king_of_cardano.md#L79-L95) (min-ADA bloat of a continuing UTxO)
- [taxonomy.md:138](../../taxonomy.md#L138) (CWC-016 Resource Exhaustion), [taxonomy.md:126](../../taxonomy.md#L126) (CWC-004 cross-ref for L-02)

### [L-01] `order` and `lp_intent` `owner` is not constrained to a verification-key credential at creation → a `Script`-owner UTXO is settle-able but never reclaimable

**Severity:** Low

**Confidence:** Confirmed

**Status:** Open

**CWC ID:** CWC-019

**Root Cause:** `owner-vk-shape-off-chain-only`

**Component:** order / lp_intent (and `spend.order_reclaim`)

**Location:**
- [spend.ak:49-52](../../contracts/shaswap/lib/shaswap/spend.ak#L49-L52) (the shared reclaim helper)
- [lp_intent.ak:219-221](../../contracts/shaswap/lib/shaswap/lp_intent.ak#L219-L221) (lp_intent reclaim defers to it)
- [types.ak:40-41](../../contracts/shaswap/lib/shaswap/types.ak#L40-L41), [lp_intent_types.ak:30-33](../../contracts/shaswap/lib/shaswap/lp_intent_types.ak#L30-L33) (`owner: Credential`, unconstrained)

**Quoted Code (`spend.ak:49-52`):**
```aiken
pub fn order_reclaim(owner: Credential, tx: Transaction) -> Bool {
  expect VerificationKey(vkh) = owner
  list.has(tx.extra_signatories, vkh)
}
```

**What It Is:**
`owner` is typed `Credential` (either `VerificationKey` or `Script`) and is never constrained at creation — spend validators do not run when an order/intent UTXO is created. The reclaim path hard-`expect`s a `VerificationKey`. In Aiken an `expect` on a failing pattern aborts the script (phase-2 failure), it is **not** a `False`. So a UTXO created with a `Script` owner can still be *settled*/*fulfilled* (those paths pay `is_payout_output(.., owner, ..)` to the `owner` credential, which may be a script) but can **never** be reclaimed — if it is never settled, it is locked forever.

**Why It Is Bad — Cardano Semantic Cited:**
Cardano credentials are a sum of `VerificationKey`/`Script`; an order datum is authored off-chain and there is no on-chain creation gate to reject a `Script` owner. The README guarantee "every well-formed order is reclaimable by its owner's signature" silently assumes a VK owner — but the validator enforces that assumption only at *reclaim* time, where it manifests as an unrecoverable lock rather than a rejection. This is the **adjacent-code heuristic** in action: the prior audit's L-01 flagged exactly this for `order`; the **new, previously-unaudited `lp_intent` subsystem reuses the same `spend.order_reclaim` helper and repeats the gap verbatim** ([lp_intent.ak:219-221](../../contracts/shaswap/lib/shaswap/lp_intent.ak#L219-L221)).

**Attack Scenario:**
No external attacker — this is a self-inflicted lock. A user (or a buggy builder) creates an order/intent with `owner = Script(h)`. If a solver/batcher never settles it (e.g. unfavourable price, or the user wanted to rely on reclaim), the funds are permanently stuck: reclaim aborts, and there is no other spend path the script owner controls. Contrast the pool `creator`, which **is** asserted to be a VK at its creation gate ([mint.ak:56-59](../../contracts/shaswap/lib/shaswap/mint.ak#L56-L59)) precisely to avoid bricking the signature-based `ClosePool`.

**Proof / Evidence:**
- Quoted code — `expect VerificationKey(vkh) = owner` aborts for any `Script` owner.
- Tests confirm the behaviour is *known* but accepted: `reclaim_script_owner` ([clearing_test.ak:404](../../contracts/shaswap/lib/shaswap/clearing_test.ak#L404)) and `reclaim_script_owner` ([lp_intent_test.ak:901](../../contracts/shaswap/lib/shaswap/lp_intent_test.ak#L901)) assert the abort — but nothing prevents *creating* such a UTXO.

**How To Fix:**
There is no on-chain creation hook for `order`/`lp_intent` (no mint), so the durable fix is documentation + builder enforcement: the off-chain builder must reject a non-VK `owner`, and the README/spec must state the constraint. If an on-chain guarantee is desired, gate order/intent creation behind a minting policy (as pools are) that asserts `expect VerificationKey(_) = datum.owner` at creation — the same fail-fast pattern as [mint.ak:56-59](../../contracts/shaswap/lib/shaswap/mint.ak#L56-L59).

**Tests To Add:**
- Negative
  - [ ] Builder-level: rejects constructing an order/intent with a `Script` owner
  - [ ] (if a creation mint is added) Rejects minting/creating an order/intent UTXO whose `owner` is a `Script`

**Additional Notes:**
Low because the only party who can lose funds is the one who created the malformed UTXO, and only if it is never settled (value leak / lock, principal preserved for the settle path). Carries forward the prior `order` L-01 and adds the new `lp_intent` instance; one coordinated documentation/builder fix closes both (same Root Cause).

- [attacks/code_quality.md:287-312](../../attacks/code_quality.md#L287-L312) (dead-code / unsafe pattern-match adjacent: owner-not-VK)

### [L-02] Standalone `LpAction` leaves a token/token pool's overhead lovelace unpinned → bounded one-time skim

**Severity:** Low

**Confidence:** Confirmed

**Status:** Open

**CWC ID:** CWC-004

**Root Cause:** `lp-action-value-not-fully-pinned`

**Component:** pool / `spend.lp_action` + `reserve_of`

**Location:**
- [spend.ak:18-24](../../contracts/shaswap/lib/shaswap/spend.ak#L18-L24) (`reserve_of` ignores lovelace for token/token pools)
- [spend.ak:170-202](../../contracts/shaswap/lib/shaswap/spend.ak#L170-L202) (the `LpAction` value constraints)

**Quoted Code (`spend.ak:18-24`):**
```aiken
pub fn reserve_of(v: Value, a: AssetId) -> Int {
  if a.policy == ada_policy_id {
    assets.lovelace_of(v) - pool_min_ada
  } else {
    utils.asset_qty(v, a)
  }
}
```

**What It Is:**
For a token/token pool (neither `asset_a` nor `asset_b` is ADA), `reserve_of` is never invoked on lovelace, so the pool's lovelace is "pure overhead" and is **not** constrained anywhere on the standalone `LpAction` path (the full-value pin is absent — the same root cause as M-01). An `LpAction` can therefore reduce the pool output's lovelace down to the ledger's true min-ADA, with the difference flowing to the actor.

**Why It Is Bad — Cardano Semantic Cited:**
The ledger enforces only that the output holds *at least* the real min-ADA; it does not pin the exact lovelace. On ADA-paired pools the ADA side *is* a reserve (`lovelace_of − pool_min_ada`) and is protected by per-share backing, but on token/token pools the lovelace is unguarded. The skimmable amount is bounded by `pool_min_ada` (2 ADA) minus the genuine ledger min-ADA for the pool's `{NFT, LP, 2 tokens}` value (~1.5 ADA), i.e. a fraction of an ADA, recoverable once.

**Attack Scenario:**
- inputs: a token/token pool UTXO (spent via `LpAction`).
- outputs: the recreated pool with reserves/held/NFT/datum unchanged but lovelace reduced to the ledger min; the skimmed lovelace lands in the actor's change.
- end-state: a one-time skim of the pool's overhead lovelace (bounded, sub-ADA). After that the pool sits at ledger min-ADA and cannot be skimmed again.

**Proof / Evidence:**
- Quoted `reserve_of` — token/token branch never reads lovelace; the `LpAction` body ([spend.ak:170-202](../../contracts/shaswap/lib/shaswap/spend.ak#L170-L202)) constrains only `asset_a`/`asset_b`/held.

**How To Fix:**
Same single fix as M-01 — pin the pool output's full value (`expect out.value == pool_exp`), which mechanically preserves the overhead lovelace and any incidental asset. See §20.0 (coordinated with M-01).

**Tests To Add:**
- Negative
  - [ ] Rejects an `LpAction` on a token/token pool that lowers the pool output's lovelace below the input's

**Additional Notes:**
Value leak, bounded and one-time, on token/token pools only → Low (per the value-leak rubric, "bounded or one-time → Medium" capped down to Low here because the magnitude is sub-ADA and self-limiting). ADA-paired pools (the common case) are unaffected.


**What It Is:**
`mint.create` locates the pool output purely by token content (NFT:1 + LP:total_lp) and validates the `PoolDatum` shape, but it never asserts the output's address — neither `payment_credential == Script(pool(S))` nor `stake_credential == Some(Inline(S))` — nor that the output holds `pool_min_ada`. The settlement/`lp_action`/`fulfill` consumers then identify the pool by NFT + `S`-tag, never by the governing `pool(S)` script hash. So *placing* a created pool at the correct address (where the `pool` validator's `k`/LP-backing checks actually govern it and where it is enumerable by the anchor) is an off-chain-builder responsibility.

**Why It Is Bad — Cardano Semantic Cited:**
Validators do not run on UTXO creation (`attacks/state.md` lifecycle), and a minting policy here does not pin the destination of the assets it mints. A pool mis-placed at a non-`pool(S)` address would not be governed by the curve validator (its `k`-check would never run) and/or would not be enumerated by the anchor (`is_tagged(S)`). However, this is **not exploitable against honest pools**: a correctly-created pool is placed at `{pool(S), S}` by the builder, and from then on continuity pins its address across every settlement/LP action ([clearing.ak:323](../../contracts/shaswap/lib/shaswap/clearing.ak#L323), [spend.ak:161](../../contracts/shaswap/lib/shaswap/spend.ak#L161)), so an attacker can never *move* a live pool off its script. The NFT is one-shot and unique, so there is no twin. The only realisable outcome is a creator self-bricking *their own* pool — no theft of others' funds.

**Attack Scenario:**
No external-attacker theft path. Failure mode: a buggy/malicious builder creates a "pool" at a wallet or wrong-script address; the creator's own seed value is then ungoverned/unsettleable (self-grief). Recorded per the Phase 5d off-chain-only-enforcement auto-finding rule so the placement invariant is tracked, not lost in prose.

**Proof / Evidence:**
- Quoted `mint.create` — `find` matches by token content only; grep confirms no `payment_credential`/`stake_credential`/`pool_min_ada` assertion anywhere in `mint.ak` (it imports only `cardano/address.{VerificationKey}`).
- Continuity does pin the address *after* creation: [clearing.ak:323](../../contracts/shaswap/lib/shaswap/clearing.ak#L323) `is_protocol_output(pool_out, pool_in.output.address)`, [spend.ak:161](../../contracts/shaswap/lib/shaswap/spend.ak#L161) `o.address == in_addr`.

**How To Fix:**
Optionally harden creation on-chain by asserting the pool output's address in `mint.create` (the policy knows `S` is not a parameter, but it can require `pool.address.stake_credential == Some(Inline(s))` if `s` is threaded in, or require a minimum lovelace `assets.lovelace_of(pool.value) >= pool_min_ada`). At minimum, document the placement invariant in the spec and enforce it in the off-chain builder; add a post-deploy ledger-query check that the pool sits at the canonical address. Because no privileged role removes this gap and no one-shot policy enforces placement, it stays Low (not downgraded to Informational) per the Phase 5d rule.

**Tests To Add:**
- Negative
  - [ ] (if address pinning is added) Rejects `Create` whose pool output is not at `{pool(S), S}`
  - [ ] (if added) Rejects `Create` whose pool output holds `< pool_min_ada` lovelace

**Additional Notes:**
Suspected / Needs Verification because exploitability against third parties is not demonstrated (continuity + one-shot NFT close the post-creation surface); the residual is a creation-time self-grief and a documentation gap. Subsumes the "pool not bound to governing script" observation: the k-check governs precisely because honest pools live at `pool(S)`.

**Confidence:** Confirmed

**Status:** Open

**Root Cause:** `permissive-burn-branch`

**Component:** pool_mint / `mint.close`

**Location:**
- [mint.ak:63-72](../../contracts/shaswap/lib/shaswap/mint.ak#L63-L72)
- [pool_mint.ak:12-16](../../contracts/shaswap/validators/pool_mint.ak#L12-L16)

**Quoted Code (`mint.ak:63-72`):**
```aiken
pub fn close(policy_id: PolicyId, tx: Transaction) -> Bool {
  list.all(
    assets.flatten(assets.restricted_to(tx.mint, [policy_id])),
    fn(triple) {
      let (_p, _n, q) = triple
      q <= 0
    },
  )
}
```

**What It Is:**
The `Close` redeemer authorizes *any* burn under the pool's policy (`q ≤ 0` for every triple) with no signer, no asset-name restriction, and no assertion that the coupled `ClosePool` spend fires. A holder of *circulating* LP tokens can burn them in a standalone tx that never touches the pool.

**Why It Is Bad — Cardano Semantic Cited:**

The only decoupled action is an LP burning their *own* circulating LP — a self-inflicted reduction of their own claim that, if anything, benefits remaining LPs (reserves unchanged, fewer real claims).

**Attack Scenario:**
A user burns LP tokens they hold via `Close` without spending the pool. They destroy their own shares; no other LP is harmed and nothing is stolen. The pool's `circ = total_lp − held` accounting (derived from the pool's held balance) is unaffected since `held` does not change.

**Proof / Evidence:**
Quoted `close`; coupling for the dangerous direction is enforced on the spend side ([spend.ak:115-128](../../contracts/shaswap/lib/shaswap/spend.ak#L115-L128)) and by `mint == 0` in every settlement/LpAction ([clearing.ak:340](../../contracts/shaswap/lib/shaswap/clearing.ak#L340), [spend.ak:153](../../contracts/shaswap/lib/shaswap/spend.ak#L153)).

**How To Fix:**
Acceptable as-is (the dangerous burns are coupled elsewhere). If tightened, require the `Close` redeemer to co-occur with the pool-spend `ClosePool` (e.g. assert the NFT is among the burned assets, forcing the pool input). Documenting the self-harm-only nature in the spec suffices.

**Tests To Add:**
- Negative
  - [ ] Confirms a standalone circulating-LP burn cannot affect the pool's held balance or reserves (already partially covered by `close_burns_circulating_lp` [mint_test.ak:190](../../contracts/shaswap/lib/shaswap/mint_test.ak#L190))

**Additional Notes:**
Tiered Informational (not Low): per the value-leak/principal-theft discipline this is neither — only the burning actor loses value, no griefing of others, no theft. Cited under CWC-014 (burn-flow) as the closest class. Carries the prior report's I-05 unchanged.

### [I-04] `lp_intent.fulfill` owner-payout uses an existence-based (`list.any`) bind; double-satisfaction safety rests entirely on the one-intent-per-tx guard

**Severity:** Informational

**Confidence:** Confirmed

**Status:** Open

**CWC ID:** CWC-028

**Root Cause:** `existence-based-binding`

**Component:** lp_intent / `pin_owner`

**Location:**
- [lp_intent.ak:71-78](../../contracts/shaswap/lib/shaswap/lp_intent.ak#L71-L78)
- [lp_intent.ak:100-105](../../contracts/shaswap/lib/shaswap/lp_intent.ak#L100-L105) (the one-intent-per-tx guard it depends on)

**Quoted Code (`lp_intent.ak:71-78`):**
```aiken
fn pin_owner(tx: Transaction, d: LpIntentDatum, owner_val: Value) -> Bool {
  list.any(
    tx.outputs,
    fn(o) {
      utils.is_payout_output(o, d.owner, d.owner_stake) && o.value == owner_val
    },
  )
}
```

**What It Is:**
Unlike the settlement path (which binds each owner output to a specific order via `BoundDatum.order_ref` — an injective per-input key), `lp_intent` binds the owner payout by *existence* ("there exists an output to `{owner, owner_stake}` with exactly `owner_val`"). Injectivity is provided solely by the one-intent-per-tx guard ([lp_intent.ak:101-105](../../contracts/shaswap/lib/shaswap/lp_intent.ak#L101-L105): exactly one input with the intent's own payment credential).

**Why It Is Bad — Cardano Semantic Cited:**
"There exists an output to Y with value X" is the classic double-satisfaction shape (`attacks/transaction_shape.md` #1): if two intents for the same owner/value were fulfilled in one tx, one owner output could satisfy both. The guard prevents this (only one intent per tx), and the value-pin + `mint == 0` + pool pin make extra owner outputs cost the batcher — so it is **safe as written**, but its safety is *transitive* (it depends on a separate guard) rather than self-contained. A future change that relaxed the one-intent rule (e.g. to batch intents) would silently reopen double-satisfaction.

**Attack Scenario:**
Not exploitable as written (the one-intent guard holds). Recorded as a brittleness/defense-in-depth note: should batching ever be added, the binding must become injective (per-intent `BoundDatum`-style key) first.

**Proof / Evidence:**
Quoted `pin_owner` + the one-intent guard at [lp_intent.ak:101-105](../../contracts/shaswap/lib/shaswap/lp_intent.ak#L101-L105). The module comment ([lp_intent.ak:66-70](../../contracts/shaswap/lib/shaswap/lp_intent.ak#L66-L70)) acknowledges the design ("With one intent per tx … the binding is injective with no per-intent NFT").

**How To Fix:**
None required now. If batching is introduced, add a per-intent injective key (mirror `BoundDatum.order_ref` from the settlement path) before allowing >1 intent per tx.

**Tests To Add:**
- Negative
  - [ ] Rejects a tx with two intent inputs (already covered by `withdraw_two_intents` [lp_intent_test.ak:456](../../contracts/shaswap/lib/shaswap/lp_intent_test.ak#L456))
  - [ ] (regression guard) If batching is added, a double-satisfaction shape with two same-owner intents must fail

**Additional Notes:**
Pairs with I-05 (both are "transitive-guarantee" patterns in `fulfill`: the pool output and the owner output are each pinned indirectly).

### [I-07] `deadline_ok` ignores `upper_bound.is_inclusive` (conservative, not exploitable)

**Severity:** Informational

**Confidence:** Confirmed

**Status:** Not Exploitable As Written

**CWC ID:** CWC-006

**Root Cause:** `is-inclusive-ignored`

**Component:** clearing / lp_intent deadline gate

**Location:**
- [clearing.ak:68-86](../../contracts/shaswap/lib/shaswap/clearing.ak#L68-L86)
- [lp_intent.ak:37-56](../../contracts/shaswap/lib/shaswap/lp_intent.ak#L37-L56)

**Quoted Code (`clearing.ak:68-86`):**
```aiken
fn finite_upper(range: Interval) -> Option<Int> {
  when range.upper_bound.bound_type is {
    Finite(u) -> Some(u)
    _ -> None
  }
}
...
fn deadline_ok(deadline: Option<Int>, tx_upper: Option<Int>) -> Bool {
  when deadline is {
    None -> True
    Some(d) ->
      when tx_upper is {
        Some(u) -> u <= d
        None -> False
      }
  }
}
```

**What It Is:**
`finite_upper` extracts the upper-bound time and discards `is_inclusive`; `deadline_ok` then checks `u <= d`. If the tx's upper bound is *exclusive*, the true latest valid time is `u − 1`, so treating it as `u` is conservative (it never admits a tx that runs past the deadline).

**Why It Is Bad — Cardano Semantic Cited:**
`validity_range` is attacker-set; the ledger only enforces inclusion, not tightness. Using the (correct) *upper* bound for a "settle-before-deadline" check is the right direction (contrast CTF 02 vesting, which wrongly used a lower bound). Ignoring `is_inclusive` errs strictly on the safe side — an exclusive `u` with `u <= d` still guarantees the actual end `< u ≤ d`. No exploit.

**Attack Scenario:**
None — the omission is conservative. Recorded for completeness and to document the deliberate bound semantics.

**Proof / Evidence:**
Quoted code; data flow confirmed `tx_upper = finite_upper(tx.validity_range)` ([clearing.ak:330](../../contracts/shaswap/lib/shaswap/clearing.ak#L330)) → `deadline_ok` at [clearing.ak:146](../../contracts/shaswap/lib/shaswap/clearing.ak#L146).

**How To Fix:**
No change required. If exactness is desired, fold `is_inclusive` into the comparison (`if is_inclusive { u } else { u - 1 } <= d`).

**Tests To Add:**
- Negative
  - [ ] (optional) A tx with an exclusive upper bound exactly at the deadline behaves as documented

**Additional Notes:**
Deadline edge cases *are* tested (`deadline_within`, `deadline_expired`, `deadline_open_tx`, `deadline_none_open_ok` [clearing_test.ak:572-599](../../contracts/shaswap/lib/shaswap/clearing_test.ak#L572-L599)); only the `is_inclusive` micro-detail is unexercised.

Fuse the input classification into a single fold producing `(order_inputs, pool_input)` in one pass, and derive the owner-output slice and remainder partition in a single output walk. Preserve the injective `order_ref` binding semantics exactly — do not trade the per-order pin for speed.

**Not applicable.** The protocol uses **no off-chain signatures** — grep for `verify_ed25519_signature | serialise_data | blake2b_224 | blake2b_256 | cheque | nonce` over the target returns **0 matches**. There are no cheques, no signed payloads, and no nonce scheme. The anti-replay property that *would* be needed is provided structurally instead: each order is bound to its unique spent `OutputReference` via `BoundDatum.order_ref == input.output_reference` ([clearing.ak:149-150](../../contracts/shaswap/lib/shaswap/clearing.ak#L149-L150)) — a single-use key that blocks both replay and double-satisfaction — and LP intents use the one-intent-per-tx guard. Redeemers are non-bearer and re-validated each run; `extra_signatories` are per-tx-body witnesses on single-use UTXOs. Phase 5e signature-payload table is therefore empty. CWC-031..035 do not apply.
