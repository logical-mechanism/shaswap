### Top three concerns

1. **C-01** — A solver can declare the pool's own **LP token** as a traded asset (`asset_b`) in the settlement redeemer; the settlement happily routes LP out of the pool to a solver-chosen output, and the pool's `k`-check never inspects LP — draining reserves via a follow-up `LpAction`.
2. **C-02** — `OrderDatum` binds neither the **bought-asset identity** nor the **target pool**, so a malicious solver can settle a user's order against an attacker-created worthless-pair pool, paying the user a worthless token while capturing their real deposit. `limit` provides no protection because it counts units of a solver-chosen asset.
3. **M-01** — Owner payout outputs are matched by `payment_credential` only; the solver chooses the **stake credential**, redirecting the payout's staking rewards (value leak).

### Production / experimental assessment

**Research / Experimental, trending Not-Ready-for-mainnet.** The author's intent (per README and revision comments) is a fully on-chain-enforced, non-custodial DEX. The two criticals show the on-chain enforcement does not yet match that intent. Fix C-01 + C-02, add the missing adversarial tests, and the design is promising.

This report is readable for a non-auditor: each finding states plainly what an attacker does and who loses money.

## 3. Contract Overview

ShaSwap is a batch-auction, constant-product DEX. A **settlement** transaction spends one pool UTXO plus a batch of order UTXOs, pays each filled order a uniquely-bound output, and leaves the residual to the pool — all in one tx. Batch-wide rules are checked **once per tx** by a withdraw-0 staking validator (the trust anchor `S`); the order and pool spend validators are thin deferrals to it.

### Validators

- **settlement** ([settlement.ak:11-18](../../contracts/shaswap/validators/settlement.ak#L11-L18)) — unparameterised withdraw-0 staking script. On `withdraw(redeemer, account, self)` it calls `clearing.run(account, redeemer, self)`. It learns its own credential `S` at runtime (the withdrawal account) and enumerates every input tagged with `S`. This is the single, global trust anchor for **all** pools and orders.
- **order(settlement_cred)** ([order.ak:12-29](../../contracts/shaswap/validators/order.ak#L12-L29)) — spend, datum `Option<OrderDatum>`. `Settle` → `spend.order_settle` (self-checks the input is `S`-tagged and a withdraw-0 for `S` is present). `Reclaim` → owner signature.
- **pool(settlement_cred)** ([pool.ak:14-38](../../contracts/shaswap/validators/pool.ak#L14-L38)) — spend, datum `Option<PoolDatum>`. `PoolSettle` → defers to settlement and owns the `k_after ≥ k_before` curve check. `LpAction` → standalone LP deposit/withdraw, mutually exclusive with a settlement. `ClosePool` → teardown of an unseeded pool.
- **pool_mint(seed: OutputReference)** ([pool_mint.ak:10-20](../../contracts/shaswap/validators/pool_mint.ak#L10-L20)) — minting policy, one-shot via the seed `OutputReference`. `Create` mints `{NFT:1, LP:total_lp}`; `Close` is burn-only. Has **no spend purpose**, so its script address is unspendable (used as the permanent `min_liq` lock).

### Protocol flow

Create (mint NFT + full LP into a validated pool UTXO) → seed via first `LpAction` (locks `min_liq` LP forever) → live trading via settlements (`PoolSettle` + `order Settle` + withdraw-0) and LP deposits/withdraws (`LpAction`) → pre-seed-only teardown (`ClosePool` + `Close` burn). Post-seed pools are immortal.

### Major assets

- Pool **NFT** (`nft_name = #"4e4654"`) and **LP** token (`lp_name = #"4c50"`), both under the pool's unique mint policy.
- An external traded pair `(asset_a, asset_b)`; either side may be ADA.

### Off-chain assumptions

Solvers compute clearings off-chain and submit settlement txs. **Solvers are explicitly untrusted** (README:4-5). No off-chain code ships in the target.

### Roles

- **Solver / batcher:** anyone; composes the settlement tx; paid only in posted tips.
- **Order owner:** posts orders, can always `Reclaim`.
- **Pool creator (VK):** can `ClosePool` a pre-seed pool only.
- **No admin / operator.** The protocol is hyperstructure-style (immutable, decentralized).

### 3.8 Builder-Bypass Question

**Is the validator safe if a malicious user bypasses any official off-chain builder? — No.** The protocol's threat model *is* "any handcrafted settlement," because solvers are untrusted and permissionless. Against a hand-built settlement tx, **C-01** (alias LP as a traded asset) drains pool reserves and **C-02** (unbound bought-asset) rugs order owners. **M-01/L-01** further let the solver pick stake credentials and attach reference scripts on outputs. The validator is therefore *not* safe against arbitrary handcrafted transactions until C-01 and C-02 are fixed.

## 8. Detailed Findings

### C-01 Settlement assets may alias the pool's own LP token → reserve drain

**Severity:** Critical

**Confidence:** Confirmed

**Status:** Open

**CWC ID:** CWC-004

**Root Cause:** `settlement-assets-alias-pool-token`

**Component:** settlement validator / `lib/shaswap/clearing`

**Location:**
- [clearing.ak:226-229](../../contracts/shaswap/lib/shaswap/clearing.ak#L226-L229)
- [clearing.ak:283-288](../../contracts/shaswap/lib/shaswap/clearing.ak#L283-L288)
- [spend.ak:57-98](../../contracts/shaswap/lib/shaswap/spend.ak#L57-L98)

**Quoted Code ([clearing.ak:226-229](../../contracts/shaswap/lib/shaswap/clearing.ak#L226-L229)):**
```aiken
pub fn run(account: Credential, r: SettlementRedeemer, tx: Transaction) -> Bool {
  // the two declared assets must be distinct (a degenerate `asset_a == asset_b`
  // would collapse the pair). Either may be ADA; at most one can be.
  expect r.asset_a != r.asset_b
```

**Quoted Code ([clearing.ak:283-288](../../contracts/shaswap/lib/shaswap/clearing.ak#L283-L288)):**
```aiken
  let pool_val_exp = pool_in.output.value
    |> assets.add(r.asset_a.policy, r.asset_a.name, net_a)
    |> assets.add(r.asset_b.policy, r.asset_b.name, net_b)
  expect pool_out.value == pool_val_exp
  // pool identity/params (and curve state) can't be mutated mid-settlement
  expect pool_out.datum == pool_in.output.datum
```

**What It Is:**
The settlement validator treats `r.asset_a` and `r.asset_b` (declared by the untrusted solver in the redeemer) as the traded pair. The *only* constraint on them is `r.asset_a != r.asset_b` ([clearing.ak:229](../../contracts/shaswap/lib/shaswap/clearing.ak#L229)). Nothing forbids declaring the pool's **own LP token** `(pool_nft.policy, lp_name)` as `asset_b`. When that happens, the pool-output pin at [clearing.ak:283-286](../../contracts/shaswap/lib/shaswap/clearing.ak#L283-L286) legitimately *moves LP out of the pool* (`net_b < 0`) into a solver-chosen owner output — and the pool's curve check in `pool_settle` reads reserves of the **datum's** real pair (e.g. `(token, ADA)`), so it never sees the LP leave. The author's own comment at [clearing.ak:276-282](../../contracts/shaswap/lib/shaswap/clearing.ak#L276-L282) claims "a solver can't strip the pool's LP (then drain via `LpAction`)"; that claim holds only for declaring the *real* pair — it is false when the LP token is declared *as* the traded asset.

**Why It Is Bad — Cardano Semantic Cited:**
Cardano asset identity is `(policy_id, asset_name)`. The settlement and the pool validator run independently on the same `Transaction` but key off *different* identities: the settlement moves `r.asset_b` (solver-chosen), while `pool_settle` measures `d.asset_a`/`d.asset_b` from the immutable `PoolDatum`. Because the pool's LP is a fungible token under the pool's own policy, and the settlement's value pin is the *only* thing guarding pool LP, aliasing LP into `asset_b` makes the pin actively authorise its removal. The `k`-check is computed over the real reserves only (`eff_a·eff_b ≥ k_in`), so removing LP while *adding* a dust of the real input asset keeps `k` non-decreasing and passes. This is the "fungible protocol-token misuse" class (KB minting §6 / bank_08) crossed with "value not preserved" (KB value §1): the pool's LP value is not preserved.

**Attack Scenario:**
Real pool P trades `(TokenX, ADA)`, holds reserves + `held` LP (large for a seeded pool). Attacker:
- Posts one order UTXO tagged `S`: `OrderDatum{owner=attacker_vk, sell_a=True, sell_amount=1, limit=0, tip=0, partial=False, deadline=None}`, funded with `1 TokenX + min-ADA`.
- Submits a settlement with redeemer `asset_a = TokenX`, `asset_b = (P.nft.policy, lp_name)` (the LP!), `pool_nft = P.nft`, `price_num = N` (huge), `price_den = 1`, `fills = [1]`.
  - `received = 1·N/1 = N` LP; `floor_ok = 1·N ≥ 0·1` ✓.
  - Owner output (attacker) = `min-ADA + N LP`, bound to the order ref ✓.
  - Pool out = pool_in `+1 TokenX − N LP`; NFT and datum preserved ✓; `mint == 0` ✓.
  - `pool_settle` (PoolSettle): reserve of `TokenX` rose by 1, ADA unchanged → `k` non-decreasing → passes ([spend.ak:91-97](../../contracts/shaswap/lib/shaswap/spend.ak#L91-L97)).
- Attacker now holds `N` LP for ~1 TokenX. In a follow-up `LpAction` withdraw they return the `N` LP and pull out reserves proportional to `N/(circ+N)` ([spend.ak:184-190](../../contracts/shaswap/lib/shaswap/spend.ak#L184-L190)) — with `N ≫ circ`, that is essentially the whole reserve.
- **End state:** attacker drains the pool's reserves; LPs lose principal.

**Proof / Evidence:**
- Quoted code above — `r.asset_a/r.asset_b` validated only for distinctness; the pin at [clearing.ak:284-285](../../contracts/shaswap/lib/shaswap/clearing.ak#L284-L285) moves whatever identity is declared.
- `pool_settle` reads the datum pair only ([spend.ak:76-79](../../contracts/shaswap/lib/shaswap/spend.ak#L76-L79)); LP is invisible to it.
- The existing guard tests [`settlement_strip_pool_lp`](../../contracts/shaswap/lib/shaswap/clearing_test.ak#L768) / [`settlement_skim_one_lp`](../../contracts/shaswap/lib/shaswap/clearing_test.ak#L773) only cover declaring the **real** pair and shrinking LP directly — they do **not** test `asset_b = LP`, so they pass while this vector is open.
- Cross-reference: `attacks/value.md:9-64` (Value Not Preserved, CWC-004); `attacks/minting.md:287-348` (Self-Collision / Fungible Auth-Token Misuse); `ctf/bank_08_self_collision.md:1-20`.

PoC test sketch (fails before fix, passes after):
```aiken

  // pool holds `lp_held` LP; redeemer declares asset_b = (nft.policy, lp_name)
  let r =
    SettlementRedeemer {
      price_num: 1_000_000, price_den: 1,
      asset_a: tok,
      asset_b: AssetId { policy: nft.policy, name: lp_name },
      pool_nft: nft, fills: [1],

  // owner output receives 1_000_000 LP; pool output loses it; k unchanged.
  clearing.run(s(), r, build_alias_lp_tx())
```

**How To Fix:**
Fence the solver-declared pair off from the pool's own identity tokens, mirroring the create-time check at [mint.ak:49-51](../../contracts/shaswap/lib/shaswap/mint.ak#L49-L51). In `clearing.run`, after `expect r.asset_a != r.asset_b`:
```aiken
// declared traded assets must be EXTERNAL — never the pool's own NFT or LP
expect r.asset_a.policy != r.pool_nft.policy
expect r.asset_b.policy != r.pool_nft.policy
```
(`pool_nft.policy` is also the LP policy, so one check excludes both NFT and LP.) Consider additionally binding `r.asset_a`/`r.asset_b`/`r.pool_nft` to the spent `PoolDatum` (see C-02's fix), which closes this and C-02 together at the cost of parsing the pool datum once.

**Tests To Add:**
- Negative
  - [ ] Reject settlement where `asset_b.policy == pool_nft.policy` (LP alias).
  - [ ] Reject settlement where `asset_a.policy == pool_nft.policy`.
  - [ ] Reject settlement where `asset_b == pool_nft` (NFT alias).

### C-02 OrderDatum binds neither bought-asset identity nor target pool → owner rug

**Severity:** Critical

**Confidence:** Confirmed

**Status:** Open

**CWC ID:** CWC-009

**Root Cause:** `order-datum-unbound-bought-asset`

**Component:** order validator / `lib/shaswap/clearing`

**Location:**
- [types.ak:32-44](../../contracts/shaswap/lib/shaswap/types.ak#L32-L44)
- [clearing.ak:142-176](../../contracts/shaswap/lib/shaswap/clearing.ak#L142-L176)

**Quoted Code ([types.ak:32-44](../../contracts/shaswap/lib/shaswap/types.ak#L32-L44)):**
```aiken

  owner: Credential,
  sell_a: Bool,
  sell_amount: Int,
  limit: Int,
  tip: Int,
  partial: Bool,
  /// Optional settlement deadline (POSIX ms). If `Some(d)`, a settlement may
  /// only include this order while the tx is valid no later than `d` (the tx's
  /// finite upper validity bound ≤ d). Owner reclaim is always allowed (§5.1),
  /// so an expired order is never stuck.
  deadline: Option<Int>,
}
```
(Note: no field names the bought asset, the sold asset, or the target pool.)

**Quoted Code ([clearing.ak:142-165](../../contracts/shaswap/lib/shaswap/clearing.ak#L142-L165)):**
```aiken
  let (sold, bought, received, d_a, d_b, floor_ok) = if order.sell_a {
    // sells asset_a, buys asset_b: received_b = f·num/den
    let recv = f * r.price_num / r.price_den
    (
      r.asset_a,
      r.asset_b,
      recv,
      f,
      -recv,
      order.sell_amount * r.price_num >= order.limit * r.price_den,
    )
  } else {
    // ... symmetric sell_a == False branch ...
  }
  expect floor_ok
```

**What It Is:**
`OrderDatum` records `sell_a` (a *direction* bit), `sell_amount`, and `limit` (a raw integer count) — but **no asset identity and no pool/NFT reference**. The asset the owner *sells* and *buys* are taken entirely from the solver's `SettlementRedeemer` (`r.asset_a`/`r.asset_b`) at [clearing.ak:143-163](../../contracts/shaswap/lib/shaswap/clearing.ak#L143-L163). The sold asset is implicitly pinned (it must exist in the order input or the value pin fails), but the **bought asset is entirely solver-chosen**. The datum comment at [types.ak:27-31](../../contracts/shaswap/lib/shaswap/types.ak#L27-L31) describes the order as being "against one pool whose pair is `(asset_a, asset_b)`" — but that pool/pair is never bound on-chain.

**Why It Is Bad — Cardano Semantic Cited:**
A spend validator only sees what the redeemer and datum encode. Since the order's redeemer (`OrderRedeemer::Settle`) carries no parameters and the datum carries no asset/pool identity, the order delegates *which assets it trades and against which pool* to the untrusted solver. `limit` cannot protect the owner because it is a unit count of a solver-chosen asset: "at least 400000" of TokenY and "at least 400000" of a worthless token both satisfy `floor_ok`. There is no continuing-output binding to the pool's datum pair, and the settlement is deliberately "curve-agnostic" (never parses `PoolDatum`), so nothing reconciles the order's economic intent with the assets actually delivered.

**Attack Scenario:**
Victim posts an order intending to sell `100 TokenX` for TokenY at a pool P(TokenX, TokenY): `OrderDatum{owner=victim, sell_a=True, sell_amount=100, limit=400000, ...}`, funded with `100 TokenX + min-ADA + tip`. Attacker:
- Creates (permissionlessly, via `pool_mint`) a pool Q trading `(TokenX, TokenZ)` where `TokenZ` is the attacker's own worthless token; seeds it with tiny `TokenX` and huge `TokenZ` reserves so the `k`-check is easy to satisfy.
- Submits a settlement spending the victim's order and pool Q with `asset_a = TokenX`, `asset_b = TokenZ`, `pool_nft = Q.nft`, price chosen so `received = 400000 TokenZ`, `fills = [100]`.
  - `floor_ok = 100·price_num ≥ 400000·price_den` ✓ (price set to meet it).
  - Victim's owner output = `min-ADA + 400000 TokenZ` (worthless); bound to the order ref ✓.
  - Pool Q out = `+100 TokenX − 400000 TokenZ`; `pool_settle` over `(TokenX, TokenZ)` passes because the attacker tuned Q's reserves.
- **End state:** the victim's `100 TokenX` is now in the attacker's pool Q; the victim holds 400000 worthless `TokenZ`. The attacker withdraws the `TokenX` from Q via `LpAction`.

**Proof / Evidence:**
- Quoted datum — no asset/pool field. Quoted clearing — bought asset = `r.asset_b`, owner protection is only `floor_ok` over a solver-chosen `received`.
- The settlement never parses `PoolDatum` (by design, [clearing.ak:19](../../contracts/shaswap/lib/shaswap/clearing.ak#L19)), so the order is never reconciled with the pool's real pair.
- Cross-reference: `attacks/datum.md:235-305` (Missing Datum-Field Validation / Datum Tampering); `attacks/state.md:120-163` (Cross-Validator Gap, CWC-023); `ctf/bank_04_lifecycle.md:1-12` / `ctf/bank_05_misconfiguration.md:1-11` (intent/identity not bound on-chain).

PoC test sketch (fails before fix, passes after):
```aiken
test settle_pays_wrong_bought_asset() fail {
  // order intends TokenY; solver declares asset_b = worthless TokenZ
  let r = SettlementRedeemer { ..base, asset_a: tok, asset_b: junk_tokenz, .. }
  clearing.run(s(), r, build_wrong_asset_tx())
}
```

**How To Fix:**
Bind the order to the assets/pool it expects. Add fields to `OrderDatum` and assert them in `check_one`:
```aiken
pub type OrderDatum {
  owner: Credential,
  pool_nft: AssetId,   // the pool this order targets
  buy:  AssetId,       // the asset the owner expects to receive
  sell: AssetId,       // the asset the owner deposits/sells
  sell_a: Bool, sell_amount: Int, limit: Int, tip: Int, partial: Bool,
  deadline: Option<Int>,
}
// in check_one / run:
expect r.pool_nft == order.pool_nft
expect bought == order.buy
expect sold == order.sell
```
A lighter alternative that also closes C-01: in `clearing.run`, parse the spent `PoolDatum` once and assert `r.asset_a == d.asset_a && r.asset_b == d.asset_b && r.pool_nft == d.nft`, then require each `OrderDatum` to name the `pool_nft` it consents to. (This trades a little curve-agnosticism for safety.)

**Tests To Add:**
- Negative
  - [ ] Reject settlement that pays the owner an asset other than the order's declared `buy`.
  - [ ] Reject settlement against a `pool_nft` the order did not consent to.
  - [ ] Reject settlement that sells an asset other than the order's declared `sell`.
- Property
  - [ ] Fuzz `r.asset_b` independent of the order's intended buy asset; settlement must reject any mismatch.

**Additional Notes:**
Principal theft from the order owner; setup (a worthless-pair pool) is trivial and permissionless → Critical. This and C-01 are two faces of the same theme (solver-declared identities under-validated) but have **distinct fixes** and **distinct victims** (pool LPs vs order owners), so they are reported separately per the anti-fabrication "split distinct issues" rule.

### M-01 Owner payout output stake credential not pinned

**Severity:** Medium

**Confidence:** Likely

**Status:** Open

**CWC ID:** CWC-018

**Root Cause:** `owner-output-stake-unpinned`

**Component:** settlement validator / `lib/shaswap/clearing`

**Location:**
- [clearing.ak:116-117](../../contracts/shaswap/lib/shaswap/clearing.ak#L116-L117)
- [clearing.ak:172-176](../../contracts/shaswap/lib/shaswap/clearing.ak#L172-L176)

**Quoted Code ([clearing.ak:114-117](../../contracts/shaswap/lib/shaswap/clearing.ak#L114-L117)):**
```aiken
  expect InlineDatum(bd) = bound.datum
  expect b: BoundDatum = bd
  expect b.order_ref == input.output_reference
  expect bound.address.payment_credential == order.owner
```

**What It Is:**
The owner payout output is matched by `payment_credential` only ([clearing.ak:117](../../contracts/shaswap/lib/shaswap/clearing.ak#L117)); its value is pinned exactly ([clearing.ak:176](../../contracts/shaswap/lib/shaswap/clearing.ak#L176)), but its `stake_credential` is unconstrained. The solver therefore chooses the stake part of every owner payout.

**Why It Is Bad — Cardano Semantic Cited:**
Cardano addresses are `(payment_credential, stake_credential)`. The owner controls spending (payment part is theirs), but staking rewards on the parked payout accrue to whatever stake credential the solver set. This is the textbook stake-credential hijack (KB authentication §5). It is a **value leak** (principal is preserved — the owner can spend the output any time), not principal theft.

**Attack Scenario:**
Solver builds an otherwise-legitimate settlement but sets each owner output's address to `(owner_payment_cred, attacker_stake_cred)`. The payout values still pass `bound.value == owner_val`. Until each owner consolidates/re-delegates the output, its staking rewards flow to the attacker's chosen credential. No signatures required.

**Proof / Evidence:**
- Quoted code — payment credential checked, stake credential absent. Contrast the *remainder* and *pool* outputs, which use full-address equality ([clearing.ak:80](../../contracts/shaswap/lib/shaswap/clearing.ak#L80), [clearing.ak:257](../../contracts/shaswap/lib/shaswap/clearing.ak#L257)) and are therefore safe.
- Cross-reference: `attacks/authentication.md:282-338` (Stake Hijack, CWC-018) and `attacks/authentication.md:427-535` (Address Perimeter Walk).

**How To Fix:**
Pin the stake credential of each owner payout to a deterministic value — `None` is the safe default for a fresh payout:
```aiken
expect bound.address == Address {
  payment_credential: order.owner,
  stake_credential: None,
}
```
If the protocol wants owners to keep delegation control, add an `owner_stake: Option<...>` to `OrderDatum` and pin to it. Reuse a single `is_payment_output(o, cred)` helper (see §20.0).

**Tests To Add:**
- Negative
  - [ ] Reject owner output whose `stake_credential` is `Some(attacker)`.
- Property
  - [ ] Fuzz `owner_output.address.stake_credential`; settlement must reject any non-`None` (or non-datum) value.

**Additional Notes:**
(value leak; principal preserved) — per §4 severity discipline this is bounded (owner can re-delegate at will, leak is rewards-only on a self-controlled output) → **Medium**, borderline Low. The KB perimeter rule defaults Medium for one-shot/short-lived outputs; kept at Medium.

- `attacks/authentication.md:282-338` (Insufficient Staking-Credential Control — CWC-018)
- `attacks/authentication.md:427-535` (Address Perimeter Walk)
- No CTF analogue (stake-hijack has no dedicated CTF in the KB; `ctf/bank_14_stake_credential_hijack.md` is the audit-machine addition for the continuing-output variant — here the affected output is a *payout*, not a continuing UTxO).

**What It Is:**

Assert the slot in each output check (and fold into the perimeter helper of §20.0):

```aiken
// likewise for bound (owner) and rem (remainder)
```

**Tests To Add:**
- Negative
  - [ ] Reject pool output with an attached `reference_script`.
  - [ ] Reject owner output / remainder with an attached `reference_script`.

**Additional Notes:**
Severity Low rather than Medium because the exact-value pin mechanically caps the bloat and the attachment is reversible (KB allows the drop-to-Low when an output value bound blocks the bloat).

**Status:** Open

**CWC ID:** CWC-019

**Root Cause:** `creator-vk-unchecked`

**Component:** minting policy / `lib/shaswap/mint`

**Location:**
- [mint.ak:40-55](../../contracts/shaswap/lib/shaswap/mint.ak#L40-L55)
- [spend.ak:113-114](../../contracts/shaswap/lib/shaswap/spend.ak#L113-L114)

**Quoted Code ([mint.ak:46-55](../../contracts/shaswap/lib/shaswap/mint.ak#L46-L55)):**
```aiken
  expect d.asset_a != d.asset_b
  expect d.asset_a.policy != policy_id
  expect d.asset_b.policy != policy_id
  expect d.fee_den > 0
  expect d.fee_num >= 0
  d.fee_num < d.fee_den
  // NOTE: d.creator is never asserted to be a VerificationKey here
```

**What It Is:**
`mint.create` validates the pool datum's NFT, pair externality, and fee range, but not that `creator` is a `VerificationKey`. `ClosePool` later does `expect VerificationKey(vkh) = d.creator` ([spend.ak:113](../../contracts/shaswap/lib/shaswap/spend.ak#L113)). If a pool is created with a `Script` creator, `ClosePool` becomes impossible for that pre-seed pool.

**Why It Is Bad — Cardano Semantic Cited:**
Validators don't run on UTXO creation; the create-time check is the only fail-fast gate for datum well-formedness (the file's own intent, [mint.ak:13-16](../../contracts/shaswap/lib/shaswap/mint.ak#L13-L16)). A `Script`-credential creator silently disables the teardown path. There is no loss of funds (the pool can still be seeded and used normally; only the pre-seed close/refund is bricked), so this is a robustness/ergonomics gap, not a vulnerability.

**Attack Scenario:**
N/A — self-inflicted misconfiguration; the affected party is the creator. Worth recording because `create` is explicitly the fail-fast validation point.

**Proof / Evidence:**
- Quoted create checks omit `creator`; `pool_close` requires VK.
- Cross-reference: `attacks/datum.md:235-305` (Missing Datum-Field Validation, CWC-019); `attacks/state.md:165-218` (Lifecycle at creation).

**How To Fix:**
Add to `mint.create`, alongside the other datum checks:
```aiken
expect VerificationKey(_) = d.creator
```

**Tests To Add:**
- Negative
  - [ ] Reject `Create` whose `PoolDatum.creator` is a `Script` credential.

**Additional Notes:**
Consistency with the "fail-fast at creation" design the module documents.

**Knowledge References:**

### O-01 Multiple independent O(N) passes over inputs/outputs in `clearing.run`

**Severity:** Optimization

**Confidence:** Suspected

**Status:** Optimization Opportunity

**CWC ID:** CWC-030

**Root Cause:** `clearing-multipass`

**Component:** `lib/shaswap/clearing`

**Location:**
- [clearing.ak:232-262](../../contracts/shaswap/lib/shaswap/clearing.ak#L232-L262)

**Quoted Code ([clearing.ak:232-256](../../contracts/shaswap/lib/shaswap/clearing.ak#L232-L256)):**
```aiken
  let tagged_inputs = list.filter(tx.inputs, fn(i) { utils.is_tagged(i.output, account) })
  let (order_inputs, pool_inputs) = list.partition(tagged_inputs, parses_as_order)
  expect [pool_in] = pool_inputs
  ...
  let tagged_outputs = list.filter(tx.outputs, fn(o) { utils.is_tagged(o, account) })
  let (pool_outs, remainders) = list.partition(tagged_outputs, fn(o) { ... })
  expect [pool_out] = pool_outs
  ...
  let n = list.length(order_inputs)
  let owner_outputs = list.take(tx.outputs, n)
```

**What It Is:**
The settlement makes several separate O(N) passes: `list.filter` then `list.partition` over inputs; `list.filter` then `list.partition` over outputs; `list.length` and `list.take` over outputs again; plus `list.zip` and the recursive `process`. Some of these traverse the same lists more than once.

**Why It Is Bad — Cardano Semantic Cited:**
On the hot path with N≈40–50 orders, redundant traversals add CPU/mem ex-units that directly tighten the batch-size ceiling. This is purely a budget concern — **no security tradeoff**.

**Attack Scenario:** N/A — optimization.

**Proof / Evidence:**
- Quoted code — two filter+partition pairs + length + take over the same input/output lists.
- Cross-reference: `optimizations/aiken_optimization_guide.md` #12 (avoid re-traversals) and #13 (validate while iterating); `optimizations/stdlib_red_flags.md` (`list.filter`/`list.partition`).

**How To Fix:**
Fuse the input classification into a single fold that simultaneously collects order inputs and the (single) pool input; likewise fuse the output classification with the owner-output `take`. **Benchmark before/after.**

**Tests To Add:**
- Benchmark
  - [ ] `bench settlement__run__midN` before and after the fold fusion (depends on I-01).

**Additional Notes:**
**Risk: low; no baseline benchmark exists — a before/after `bench` is required first** (Phase 9 rule). Do not refactor the hot path without the I-01 baseline. Expected benefit: a constant-factor reduction in input/output traversals (rough, unquantified without a baseline).

**Knowledge References:**
- `optimizations/aiken_optimization_guide.md:1` (benchmark first), guide #12/#13 (re-traversal / validate-while-iterating)
- `optimizations/stdlib_red_flags.md:1-20` (`list.filter`, `list.partition`)
- No CTF analogue.
- `taxonomy.md:152` (CWC-030)

**Tags:** `optimization`, `re-traversal`, `hot-path`, `CWC-030`
