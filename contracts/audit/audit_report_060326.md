## 3. Contract Overview

ShaSwap is a fully-decentralized, non-custodial, MEV-resistant **batch-auction DEX**. Untrusted solvers compute a single uniform clearing price off-chain for a batch of orders against one constant-product pool; the validators only *verify* the settlement.

**Validators / scripts:**

- **`settlement`** ([validators/settlement.ak:11-19](../../contracts/shaswap/validators/settlement.ak#L11-L19)) — an **unparameterised withdraw-0 staking script** (the immutable trust anchor). On a `withdraw`, it learns its own credential `S` as the withdraw account and calls `clearing.run(S, redeemer, tx)`, which enumerates every input tagged with stake credential `S`, classifies each (order vs the sole pool), and enforces the batch rules. `else → fail`.
- **`order(settlement_cred)`** ([validators/order.ak:12-29](../../contracts/shaswap/validators/order.ak#L12-L29)) — user-facing spend validator. `Settle` self-checks its own `S` tag and that the settlement withdrawal is present (deferral); `Reclaim` is owner-VK-signature-only. `else → fail`.
- **`pool(settlement_cred)`** ([validators/pool.ak:14-39](../../contracts/shaswap/validators/pool.ak#L14-L39)) — constant-product pool spend validator. `PoolSettle` checks `k_after ≥ k_before` (with the static fee) and continuity; `LpAction` runs the value-derived LP invariant and asserts mutual exclusion with settlement (`!withdrawal_present`); `ClosePool` tears down a pre-seed pool. `else → fail`.
- **`pool_mint(seed)`** ([validators/pool_mint.ak:10-21](../../contracts/shaswap/validators/pool_mint.ak#L10-L21)) — one-shot pool-creation/closure policy (parameterised by a seed `OutputReference`). `Create` mints `{NFT:1, LP:total_lp}` into a validated pool UTxO; `Close` is burn-only. `else → fail` — which also makes the policy's own script address **unspendable**, the永-lock target for `min_liq`.

**Protocol flow narrative:**
1. *Create* — `pool_mint.Create` consumes the seed, mints the NFT + full LP supply into one pool UTxO at address `(payment=pool_script, stake=S)`, and validates the initial `PoolDatum` (external non-degenerate pair, fee in range, NFT identity, VK creator).
2. *Seed (first LP)* — `pool.LpAction` first deposit mints `floor(sqrt(res_a·res_b))` shares (value-derived) and permanently locks `min_liq` LP at the mint-policy address.
3. *Trade (settlement)* — users post order UTxOs at `(payment=order_script, stake=S)`. A solver builds a tx with the pool + N orders + a withdraw-0 for `S`; `clearing.run` pins every owner payout, the pool residual, and any partial-fill remainders exactly, while `pool.PoolSettle` independently enforces `k`.
4. *Deposit / withdraw* — `pool.LpAction` (standalone, mutually exclusive with settlement) moves LP between pool and user with per-share-backing-non-decreasing.
5. *Terminal* — `pool.ClosePool` + `pool_mint.Close` tear down a never-seeded pool (creator sig, burn NFT + full LP). Post-seed pools are immortal (locked `min_liq` can never be reassembled). Orders are always reclaimable by the owner.

**Major assets:** pool NFT (`policy = pool_mint hash`, name `#"4e4654"`), LP token (same policy, name `#"4c50"`, supply `total_lp = 9_223_372_036_854_775_807`), and arbitrary external traded pairs (ADA or native tokens).

**Expected tx shapes:** see §5. **Off-chain assumptions:** see §3.8 and §18. **User roles:** order owner, LP, pool creator, solver (untrusted). **Admin roles:** none. **Hyperstructure assumptions:** the protocol is admin-free; `S` is registered at deploy and never delegated (README:57-63); no upgrade key.

### 3.8 Builder-Bypass Question

**Is the validator safe if a malicious user bypasses any official off-chain builder? — Yes.** The protocol is explicitly designed for adversarial, handcrafted transactions: solvers are *untrusted* and there is no privileged builder. Every value movement is pinned on-chain — owner payouts (`bound.value == owner_val`, [clearing.ak:188](../../contracts/shaswap/lib/shaswap/clearing.ak#L188)), the pool residual (`pool_out.value == pool_val_exp`, [clearing.ak:327](../../contracts/shaswap/lib/shaswap/clearing.ak#L327)), partial-fill remainders (`rem.value == exp_value`, [clearing.ak:91](../../contracts/shaswap/lib/shaswap/clearing.ak#L91)), `mint == 0` ([clearing.ak:315](../../contracts/shaswap/lib/shaswap/clearing.ak#L315)) — so ledger value conservation forces the only free residual to be the posted tips. The pool's `k` is independently re-checked by `pool.PoolSettle`, and the pool spend validator necessarily runs because the pool is a spent input. The one residual user-side caveat is **L-01** (creation-time owner shape), which is a creation gap, not a builder-bypass gap. So: a handcrafted Cardano transaction cannot extract trader funds, pool reserves, or free tokens.

### Low

### [L-01] Order `owner` is not constrained to a verification-key credential at creation → a `Script`-credential owner yields a non-reclaimable order

**Severity:** Low

**Confidence:** Likely

**Status:** Open

**CWC ID:** CWC-019

**Root Cause:** `order-owner-vk-unconstrained`

**Component:** order validator / types

**Location:**
- [lib/shaswap/types.ak:40-53](../../contracts/shaswap/lib/shaswap/types.ak#L40-L53)
- [lib/shaswap/spend.ak:49-52](../../contracts/shaswap/lib/shaswap/spend.ak#L49-L52)
- [validators/order.ak:19-24](../../contracts/shaswap/validators/order.ak#L19-L24)

**Quoted Code (`lib/shaswap/spend.ak:48-52`):**
```aiken
/// Order `Reclaim`: owner signature alone (§5.1, non-custodial).
pub fn order_reclaim(owner: Credential, tx: Transaction) -> Bool {
  expect VerificationKey(vkh) = owner
  list.has(tx.extra_signatories, vkh)
}
```

**What It Is:**
`OrderDatum.owner` is typed as a `Credential` ([types.ak:41](../../contracts/shaswap/lib/shaswap/types.ak#L41)), which can be either `VerificationKey(_)` or `Script(_)`. Order UTxOs are created off-chain with no on-chain creation gate (a spend validator does not run on UTxO creation — only on spend), so nothing forces `owner` to be a verification-key credential. The reclaim path `order_reclaim` hard-`expect`s `VerificationKey(vkh)`. If an order is created with a `Script`-credential owner, the reclaim branch can never succeed (the `expect` aborts), and the order's only remaining exit is to be settled. If that order is never settled (e.g. an unsatisfiable `limit`, a deadline that passes, or simply no solver picks it up), the funds are locked forever.

**Why It Is Bad — Cardano Semantic Cited:**
Validators do not run on UTxO creation, only on spend — so the protocol cannot validate the initial `OrderDatum.owner` shape at the moment the order is created (see `attacks/state.md` §4 lifecycle). The non-custodial guarantee ("every well-formed order is reclaimable by its owner's signature", README:32) silently depends on `owner` being a VK credential, but that precondition is enforced nowhere on-chain and is not documented as an off-chain builder requirement. Reclaim is the protocol's liveness safety-valve; removing it (via a Script owner) re-introduces a lock-forever path for an order that the auction never clears.

**Attack Scenario:**
This is self-inflicted rather than an attacker-against-victim vector — an attacker cannot force another user's order to carry a `Script` owner. Concretely:
- A user (or a buggy builder) creates an order UTxO at `(payment=order_script, stake=S)` with `OrderDatum.owner = Script(h)` for any script hash `h`.
- The order's `limit` is set high enough that no clearing price satisfies the floor (or the market simply never matches it).
- The owner attempts `Reclaim`: `order_reclaim` hits `expect VerificationKey(vkh) = owner` on a `Script` credential and the script aborts → reclaim impossible.
- End state: the order's deposited assets + tip + min-ADA are locked forever. No funds are *stolen*; they are *bricked*.

**Proof / Evidence:**
- Quoted code above shows the unconditional `expect VerificationKey(vkh) = owner`.
- The settlement path `is_payout_output(bound, order.owner)` ([clearing.ak:129](../../contracts/shaswap/lib/shaswap/clearing.ak#L129), [utils.ak:30-32](../../contracts/shaswap/lib/shaswap/utils.ak#L30-L32)) *accepts* a `Script` owner (it pins `payment_credential: owner`), so settlement of such an order succeeds — confirming the asymmetry: settle-yes, reclaim-no.
- Contrast: the pool `creator` field *is* asserted to be a VK credential at its creation gate ([mint.ak:59](../../contracts/shaswap/lib/shaswap/mint.ak#L59), prior finding I-03), precisely to avoid bricking the signature-based `ClosePool`. Orders have no equivalent gate because they have no creation gate at all.

**How To Fix:**
There is no on-chain creation hook for orders, so the realistic fixes are:
- **Document + enforce off-chain (preferred):** state in the spec / builder that `OrderDatum.owner` MUST be `VerificationKey(_)`, and have the official order-builder reject `Script` owners. Record this as a builder invariant (see §18 / §3.8).
- **Defensive on-chain note:** if a future revision adds an order-creation mint gate (e.g. an order validity token), assert `expect VerificationKey(_) = datum.owner` there, mirroring [mint.ak:59](../../contracts/shaswap/lib/shaswap/mint.ak#L59).
- Optionally, broaden `order_reclaim` to also honour a `Script`-credential owner via a script-witness (a withdrawal/spend of that script in the same tx) so a script-owned order is still reclaimable — only if script owners are a desired feature.

**Tests To Add:**
- Negative
  - [ ] `test fail__reclaim_script_owner()` — an order with `owner: Script(_)` cannot be reclaimed (documents the lock).
- Positive

### [I-05] `mint Close` permits a standalone circulating-LP burn decoupled from pool teardown

**Severity:** Informational

**Confidence:** Likely

**Status:** Open

**CWC ID:** CWC-014

**Root Cause:** `lp-burn-decoupled`

**Component:** mint policy

**Location:**
- [lib/shaswap/mint.ak:64-72](../../contracts/shaswap/lib/shaswap/mint.ak#L64-L72)

**Quoted Code (`lib/shaswap/mint.ak:63-72`):**
```aiken
/// Close: burn-only — no positive quantity may be minted under this policy.
pub fn close(policy_id: PolicyId, tx: Transaction) -> Bool {
  list.all(
    assets.flatten(assets.restricted_to(tx.mint, [policy_id])),
    fn(triple) {
      let (_p, _n, q) = triple
      q <= 0
    },
  )
}
```

**What It Is:**
The `Close` mint branch only asserts that no positive quantity is minted under the policy. A holder of *circulating* LP tokens (LP that has left the pool into a wallet) can therefore submit a transaction with `MintRedeemer = Close` that burns their own LP **without spending the pool UTxO**. Because the pool's circulating-supply notion is value-derived as `total_lp − held_in_pool` ([spend.ak:177-178](../../contracts/shaswap/lib/shaswap/spend.ak#L177-L178)) — i.e. it counts only LP physically in the pool — burning LP outside the pool does not change the pool's accounting. The reserves backing those burned shares remain in the pool but become permanently unclaimable (no LP exists to redeem them).

**Why It Is Bad — Cardano Semantic Cited:**
`tx.mint` quantities can be negative (burn) and the ledger lets anyone burn tokens they hold. Here the burn is decoupled from the pool's state machine: the pool validator never runs for a pure-burn tx, so it cannot reconcile circulating supply against actual token supply. The effect is self-harm — the burner forfeits their claim and slightly over-collateralizes the remaining LPs' redemption value — but it is an unintended capability of the mint policy and worth recording.

**Attack Scenario:**
- An LP holds `x` circulating LP tokens in their wallet.
- They submit a tx with `pool_mint.Close`, `mint = {LP: −x}`, no pool input.
- `mint.close` passes (all quantities ≤ 0). The LP is burned.
- End state: the burner loses their `x` shares; the reserves those shares could have redeemed stay locked in the pool forever. No third party is harmed (the pool's `circ = total_lp − held` is unchanged, so other LPs' withdrawals proceed as before). There is **no theft** — only self-inflicted value lock.

**Proof / Evidence:**
- Quoted `close` accepts any all-non-positive mint under the policy with no pool-input or signer requirement.
- `lp_action` requires `assets.is_zero(tx.mint)` ([spend.ak:153](../../contracts/shaswap/lib/shaswap/spend.ak#L153)), so a burn **cannot** be combined with a deposit/withdraw — ruling out any manipulation of an in-flight LP action. The NFT cannot be burned this way because it lives in the pool and the pool's spend validators pin its continuity except in `ClosePool` (which requires `held == total_lp` + creator sig). So the only "free" burn is circulating LP — confirming self-harm only.

**How To Fix:**
Optional hardening (the current behaviour is not exploitable against others):
- Require a pool input for any burn, so the pool validator can reconcile supply — but this conflicts with the deliberate tx-level-minter split. Alternatively,
- Document explicitly that circulating LP is burnable and that doing so locks the corresponding reserves (a property, not a bug), and add a test pinning the behaviour. Most protocols accept "you may burn your own LP and forfeit its claim" as benign.

**Tests To Add:**
- Negative / property
  - [ ] `test lp_burn_locks_reserves()` — a standalone `Close` burning circulating LP succeeds and the pool's reserves are unaffected (documents the property).
  - [ ] Confirm a burn combined with `LpAction` is rejected (`assets.is_zero(tx.mint)`) — likely already implied by `stray_mint`.

**Additional Notes:**
- Tiered Informational (not Low) because the only party who can lose value is the actor performing the burn; there is no griefing of other LPs and no theft (per §4 value-leak/principal-theft discipline, this is neither — it is self-burn). Cited under CWC-014 (burn-flow) as the closest class.

**Knowledge References:**
- [attacks/minting.md:353-445](../../attacks/minting.md#L353-L445) (missing-burn-verification / burn-branch-returns-True family — here the burn-only branch is intentional but uncoupled)
- [patterns/tx_level_minter.md:80-90](../../patterns/tx_level_minter.md#L80-L90) (mint endpoint defers to spend; audit concern: the mint must not authorize anything the spend would forbid)
- [taxonomy.md:136](../../taxonomy.md#L136) (CWC-014 Burn Verification Failure)
