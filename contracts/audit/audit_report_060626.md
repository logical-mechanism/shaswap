## 3. Contract Overview

ShaSwap is a fully-decentralized, non-custodial, MEV-resistant **batch-auction DEX**. Untrusted solvers compute a single uniform clearing price for a batch of orders against one constant-product pool off-chain; the validators only *verify* the settlement. There is **no admin, operator, batcher allow-list, upgrade, or pause**.

**Validators / scripts:**

- **`settlement`** ([validators/settlement.ak:12-28](../../shaswap/validators/settlement.ak#L12-L28)) — an **unparameterised withdraw-0 staking script** (the immutable trust anchor). On `withdraw` it learns its own credential `S` as the withdraw account and calls `clearing.run(S, redeemer, tx)`, which enumerates every input tagged with stake-credential `S`, classifies each (order vs the sole pool), and enforces the batch rules. `publish` permits only `RegisterCredential` (never de-register/delegate). `else → fail`.
- **`order(S)`** ([validators/order.ak:12-29](../../shaswap/validators/order.ak#L12-L29)) — user-facing spend validator. `Settle` self-checks its own `S` tag and that the settlement withdrawal is present (deferral to the anchor); `Reclaim` is owner-VK-signature-only. `else → fail`.
- **`pool(S)`** ([validators/pool.ak:14-39](../../shaswap/validators/pool.ak#L14-L39)) — constant-product pool spend validator. `PoolSettle` checks `k_after ≥ k_before` with the static fee *and* the Rev-25 two-sided price pin, and defers the batch to `S`; `LpAction` runs the value-derived LP invariant and asserts mutual exclusion with settlement (`!withdrawal_present(S)`); `ClosePool` tears down a pre-seed pool. `else → fail`.
- **`pool_mint(seed)`** ([validators/pool_mint.ak:10-21](../../shaswap/validators/pool_mint.ak#L10-L21)) — one-shot pool create/close policy (parameterised by a seed `OutputReference`). `Create` mints `{NFT:1, LP:total_lp}` into a validated pool UTxO; `Close` is burn-only. `else → fail` — which also makes the policy's own script address unspendable, the permanent-lock target for `min_liq`.
- **`lp_intent(S)`** ([validators/lp_intent.ak:18-35](../../shaswap/validators/lp_intent.ak#L18-L35)) — batcher-fulfilled LP deposit/withdraw *intent* (the newest subsystem, Rev 22, sitting at a non-`S` enterprise address). `Fulfill` pins the owner payout exactly, asserts the settlement withdraw-0 for `S` is **absent** (forcing the coupled pool spend to be `LpAction`, where per-share backing runs), and applies the Rev-25 exact at-ratio / proportional pins; `ReclaimLp` is owner-VK-signature-only.

**Protocol flow narrative:** *create* (`pool_mint.Create` → seeded pool at `(payment = pool_script, stake = S)` with NFT + full LP) → *seed* (`pool.LpAction` first deposit, `floor(sqrt(rₐ·r_b))` shares, permanent `min_liq` lock at the unspendable mint-policy address) → *trade* (users post `order(S)` UTxOs tagged `S`; a solver settles one pool + N orders via the `S` withdraw-0; `clearing.run` pins every owner payout, the pool residual, and partial-fill remainders exactly while `pool.PoolSettle` independently re-checks `k` and the price pin) / *provide liquidity* (`pool.LpAction` directly, or `lp_intent(S).Fulfill` via a batcher) → *terminal* (`pool.ClosePool` + `pool_mint.Close` only while unseeded; post-seed pools are immortal because `min_liq` LP can never be reassembled). Orders/intents are always owner-reclaimable.

**Major assets:** pool NFT (`policy = pool_mint hash`, name `#"4e4654"` = "NFT"), LP token (same policy, name `#"4c50"` = "LP", supply `total_lp = 9_223_372_036_854_775_807`), and arbitrary external traded pairs (ADA or native tokens; either side may be ADA).

**Off-chain assumptions:** see §3.8 and §18. **User roles:** order owner, LP, pool creator, solver/batcher (all untrusted). **Admin roles:** none. **Hyperstructure assumptions:** admin-free; `S` is registered at deploy and never delegated; no upgrade key.

### 3.8 Builder-Bypass Question

**Is the validator safe if a malicious user bypasses any official off-chain builder? — Yes.** The protocol is explicitly designed for adversarial, handcrafted transactions: solvers and batchers are *untrusted* and there is no privileged builder. Every value movement is pinned on-chain — owner payouts (`expect bound.value == owner_val`, [clearing.ak:233](../../shaswap/lib/shaswap/clearing.ak#L233)), the pool residual (`expect pool_out.value == pool_val_exp`, [clearing.ak:382](../../shaswap/lib/shaswap/clearing.ak#L382)), partial-fill remainders (`expect rem.value == exp_value`, [clearing.ak:109](../../shaswap/lib/shaswap/clearing.ak#L109)), the LP-intent owner/pool values ([lp_intent.ak:175](../../shaswap/lib/shaswap/lp_intent.ak#L175), [lp_intent.ak:222](../../shaswap/lib/shaswap/lp_intent.ak#L222)), and `mint == 0` ([clearing.ak:370](../../shaswap/lib/shaswap/clearing.ak#L370)) — so ledger value conservation forces the only free residual to be the posted tips. The pool's `k` and the two-sided price pin are independently re-checked by `pool.PoolSettle`, which necessarily runs because the pool is a spent input. The sole residual user-side caveat is **L-01** (creation-time owner shape), which is a creation gap, not a builder-bypass gap. A handcrafted Cardano transaction cannot extract trader funds, pool reserves, or free tokens, nor replay a payout.

**Quoted Code (`lib/shaswap/spend.ak:72-75`):**
```aiken
/// Order `Reclaim`: owner signature alone (§5.1, non-custodial).
pub fn order_reclaim(owner: Credential, tx: Transaction) -> Bool {
  expect VerificationKey(vkh) = owner
  list.has(tx.extra_signatories, vkh)
}
```

**What It Is:**
`OrderDatum.owner` and `LpIntentDatum.owner` are typed as `Credential` ([types.ak:41](../../shaswap/lib/shaswap/types.ak#L41), [lp_intent_types.ak:32](../../shaswap/lib/shaswap/lp_intent_types.ak#L32)), which can be `VerificationKey(_)` or `Script(_)`. Order/intent UTxOs are created off-chain with no on-chain creation gate (a spend validator does not run on UTxO creation — only on spend), so nothing forces `owner` to be a verification-key credential. Both reclaim paths route through `order_reclaim`, which hard-`expect`s `VerificationKey(vkh)`. If a UTxO is created with a `Script`-credential owner, the reclaim branch can never succeed (the `expect` aborts), and the UTxO's only remaining exit is to be settled/fulfilled. If it never is (an unsatisfiable `limit`, a passed deadline, or simply no solver matches it), the funds are locked forever. `lp_intent` re-uses `spend.order_reclaim` verbatim ([lp_intent.ak:240-242](../../shaswap/lib/shaswap/lp_intent.ak#L240-L242)), so the new subsystem inherits the same gap (adjacent-code heuristic).

**Why It Is Bad — Cardano Semantic Cited:**
Cardano credentials are a sum of `VerificationKey`/`Script`; a datum is authored off-chain and **validators do not run on UTxO creation, only on spend**, so the protocol cannot reject a `Script` owner at the moment the order is created (see [attacks/state.md:165-223](../../attacks/state.md#L165-L223) lifecycle). Signature-based reclaim is the protocol's liveness safety-valve, and `extra_signatories` carries verification-key hashes only — a `Script` owner can never satisfy it. The non-custodial guarantee ("every well-formed order is reclaimable by its owner's signature", [README.md:32-37](../../shaswap/README.md#L32-L37)) silently depends on `owner` being a VK credential.

**Attack Scenario:**
Self-inflicted, not attacker-against-victim (an attacker cannot force another user's order to carry a `Script` owner):
- A user (or a buggy builder) creates an order/intent UTxO at the script address with `owner = Script(h)` for some script hash `h`.
- The order's `limit` is unsatisfiable, or no solver matches it before its deadline.
- The owner attempts `Reclaim`/`ReclaimLp`: `order_reclaim` aborts at `expect VerificationKey(vkh) = owner` → reclaim impossible.
- End state: the deposited assets + tip + min-ADA are bricked. No funds are *stolen*; they are *locked*.

**Proof / Evidence:**
- Quoted code shows the unconditional `expect VerificationKey(vkh) = owner`.
- The settle/fulfill paths *accept* a `Script` owner: `is_payout_output(bound, order.owner, order.owner_stake)` ([utils.ak:32-42](../../shaswap/lib/shaswap/utils.ak#L32-L42)) pins `payment_credential: owner` without a VK check — confirming the asymmetry (settle-yes, reclaim-no).
- Contrast: the pool `creator` field *is* asserted VK at its creation gate ([mint.ak:59](../../shaswap/lib/shaswap/mint.ak#L59)), precisely because `ClosePool` is signature-based. Orders/intents have no creation gate at all.
- Tests confirm the behaviour is *known and accepted*: [clearing_test.ak:438](../../shaswap/lib/shaswap/clearing_test.ak#L438) (`reclaim_script_owner`) and [lp_intent_test.ak:1005](../../shaswap/lib/shaswap/lp_intent_test.ak#L1005) (`reclaim_script_owner`) assert the abort.

**How To Fix:**
There is no on-chain creation hook for orders/intents (no mint), so the durable fix is documentation + builder enforcement:
- **Preferred:** state in the spec and the official builders that `owner` MUST be `VerificationKey(_)`, and have the order/intent builders reject `Script` owners (the demo builder already does — see §18). Record it as a builder invariant.
- **Defensive on-chain:** if a future revision gates order/intent creation behind a minting policy (as pools are), assert `expect VerificationKey(_) = datum.owner` there — the same fail-fast pattern as [mint.ak:56-59](../../shaswap/lib/shaswap/mint.ak#L56-L59).
- Optionally broaden reclaim to honour a `Script` owner via a same-tx script witness, only if script owners become a desired feature.

**Tests To Add:**
- Negative
  - [ ] `test fail__reclaim_script_owner()` (order) — already present at [clearing_test.ak:438](../../shaswap/lib/shaswap/clearing_test.ak#L438); keep as the lock-documentation test.
  - [ ] `test fail__reclaim_script_owner()` (lp_intent) — already present at [lp_intent_test.ak:1005](../../shaswap/lib/shaswap/lp_intent_test.ak#L1005).
- Property
  - [ ] Fuzz `owner` credential variants; assert reclaim succeeds iff `owner` is `VerificationKey` and the matching key signs.

**Additional Notes:**
- Borderline severity: lock-forever is normally High, but this is **self-inflicted** (the creator chooses `owner`), cannot be triggered against a third party, is naturally avoided by any sane builder, and the principal is preserved for the settle/fulfill path (value leak, not principal theft). Per §4 severity discipline → tiered **Low**, consistent with both prior in-tree audits.

### [I-02] `mint.close` permits a standalone circulating-LP burn decoupled from pool teardown (self-harm only)

**Severity:** Informational

**Confidence:** Likely

**Status:** Design Tradeoff

**CWC ID:** CWC-014 (from [taxonomy.md:136](../../taxonomy.md#L136))

**Root Cause:** `lp-burn-decoupled`

**Component:** pool_mint policy

**Location:**
- [lib/shaswap/mint.ak:81-89](../../shaswap/lib/shaswap/mint.ak#L81-L89)

**Quoted Code (`lib/shaswap/mint.ak:81-89`):**
```aiken
pub fn close(policy_id: PolicyId, tx: Transaction) -> Bool {
  list.all(
    assets.flatten(assets.restricted_to(tx.mint, [policy_id])),
    fn(triple) {
      let (_p, _n, q) = triple
      q <= 0
    },
  )
}
```

**What It Is:**
The `Close` mint branch only asserts that no positive quantity is minted under the policy. A holder of *circulating* LP (LP that has left the pool into a wallet) can submit a tx with `MintRedeemer = Close`, `mint = {LP: -x}`, and **no pool input**. The pool's circulating-supply notion is value-derived as `total_lp - held_in_pool` ([spend.ak:235](../../shaswap/lib/shaswap/spend.ak#L235)), counting only LP physically in the pool; burning LP outside the pool does not change the pool's accounting, so the reserves backing those burned shares stay in the pool and become permanently unclaimable.

**Why It Is Bad — Cardano Semantic Cited:**
`tx.mint` quantities can be negative (burn) and the ledger lets anyone burn tokens they hold. Here the burn is decoupled from the pool's state machine: the pool validator never runs for a pure-burn tx, so it cannot reconcile circulating supply against actual token supply. The effect is self-harm — the burner forfeits their claim and slightly over-collateralizes the remaining LPs — but it is an unintended capability worth recording.

**Attack Scenario:**
An LP holds `x` circulating LP, submits `pool_mint.Close` with `mint = {LP: -x}` and no pool input. `mint.close` passes (all quantities ≤ 0); the LP is burned. End state: the burner loses their `x` shares; the reserves those shares could have redeemed stay locked forever. No third party is harmed (`circ = total_lp - held` is unchanged for everyone else). **No theft** — self-inflicted value lock only.

**Proof / Evidence:**
- Quoted `close` accepts any all-non-positive mint with no pool-input or signer requirement.
- `lp_action` requires `assets.is_zero(tx.mint)` ([spend.ak:211](../../shaswap/lib/shaswap/spend.ak#L211)), so a burn cannot be combined with a deposit/withdraw — ruling out manipulation of an in-flight LP action.
- The NFT cannot be burned this way: it lives in the pool and its continuity is pinned by `PoolSettle`/`LpAction` except via `ClosePool` (which requires `held == total_lp` + creator sig + full NFT/LP burn, [spend.ak:173-186](../../shaswap/lib/shaswap/spend.ak#L173-L186)). So the only "free" standalone burn is circulating LP — confirming self-harm only.
- A test pins the property: [mint_test.ak:206](../../shaswap/lib/shaswap/mint_test.ak#L206) (`close_burns_circulating_lp`).

**How To Fix:**
The current behaviour is not exploitable against others; this is documented as intentional via the doc-comment at [mint.ak:74-80](../../shaswap/lib/shaswap/mint.ak#L74-L80). Keep the property test and the docstring; no code change required. (If desired, require a pool input for any burn so the pool can reconcile supply — but that conflicts with the deliberate tx-level-minter split.)

**Tests To Add:**
- Negative / property
  - [ ] `test lp_burn_locks_reserves()` — a standalone `Close` burning circulating LP succeeds and the pool's reserves/`circ` are unaffected (documents the property); partially covered by `close_burns_circulating_lp`.

**Additional Notes:**
- Tiered Informational + Design Tradeoff (not Low): the only party who can lose value is the actor performing the burn; no griefing of other LPs and no theft (per §4 value-leak/principal-theft discipline this is neither — it is self-burn). Cited under CWC-014 (burn flow) as the closest class; carried forward from the prior in-tree I-03/I-05.

### [I-03] Two divisions lack an explicit positivity guard (lp_intent withdraw `circ_in`; public `get_amount_out`)

**Severity:** Informational

**Confidence:** Confirmed

**Status:** Not Exploitable As Written

**CWC ID:** CWC-008 (from [taxonomy.md:130](../../taxonomy.md#L130))

**Root Cause:** `defensive-division-guard`

**Component:** lp_intent fulfillment / pool curve helper

**Location:**
- [lib/shaswap/lp_intent.ak:163-165](../../shaswap/lib/shaswap/lp_intent.ak#L163-L165) (withdraw branch, no `expect circ_in > 0`)
- [lib/shaswap/lp_intent.ak:188](../../shaswap/lib/shaswap/lp_intent.ak#L188) (deposit branch — has the guard)
- [lib/shaswap/spend.ak:48-57](../../shaswap/lib/shaswap/spend.ak#L48-L57) (`get_amount_out`)

**Quoted Code (`lib/shaswap/lp_intent.ak:163-165`):**
```aiken
let circ_in = total_lp - held_in
expect released_a == res_a_in * l / circ_in
expect released_b == res_b_in * l / circ_in
```

**What It Is:**
Two divisions divide by a quantity that is positive by conservation but is not asserted positive locally. (1) The LP-intent `LpWithdraw` branch divides by `circ_in = total_lp - held_in` with no preceding `expect circ_in > 0` — yet the sibling `LpDeposit` branch ([lp_intent.ak:188](../../shaswap/lib/shaswap/lp_intent.ak#L188)) *does* guard it. (2) The public `get_amount_out` ([spend.ak:48-57](../../shaswap/lib/shaswap/spend.ak#L48-L57)) divides by `res_in * fee_den + dx * g` with no internal guard. In both cases a zero denominator would *abort* the Plutus script (a safe failure, never a wrong result).

**Why It Is Bad — Cardano Semantic Cited:**
Plutus integer `/` by zero aborts script evaluation (it does not return), so neither can mis-compute a release — only self-abort. Neither is reachable on-chain:
- Withdraw: `expect l >= 1` ([lp_intent.ak:147](../../shaswap/lib/shaswap/lp_intent.ak#L147)) plus the ledger invariant `held + circulating == total_lp` (LP minted exactly once at create, `mint == 0` on every spend) means a withdraw carrying `l >= 1` proves `circ_in = total_lp - held_in >= l >= 1 > 0`. Even if forced, `lp_action`'s `held_out <= total_lp` ([spend.ak:243](../../shaswap/lib/shaswap/spend.ak#L243)) rejects the result.
- `get_amount_out`: both on-chain callers ([spend.ak:153](../../shaswap/lib/shaswap/spend.ak#L153), [spend.ak:156](../../shaswap/lib/shaswap/spend.ak#L156)) are gated by `net_a > 0`/`net_b > 0` (so `dx > 0`) and by `expect d.fee_num < d.fee_den` ([spend.ak:122](../../shaswap/lib/shaswap/spend.ak#L122)) giving `g > 0`, so `dx * g > 0` and the denominator is strictly positive even if `res_in == 0`.

Aiken `Int` is arbitrary-precision (bignum), so the `total_lp`-scale products (e.g. `res_a_in * res_b_in * fee_den²` ≈ 1e30 in the k-check) are exact — the only arithmetic abort surface is the zero denominator, already excluded.

**Attack Scenario:**
None reachable. The only effect of a zero denominator (which requires an impossible token configuration) would be an immediate self-abort. The public `get_amount_out` is documented as the off-chain↔on-chain parity helper; a *parity harness* that called it with `dx == 0 && res_in == 0` would crash rather than return — an off-chain footgun, not an on-chain vector.

**Proof / Evidence:**
- Quoted asymmetry: the deposit branch guards `circ_in > 0`, the withdraw branch does not.
- On-chain call-site guards quoted above (`l >= 1`, `net_* > 0`, `fee_num < fee_den`).

**How To Fix:**
For symmetry and refactor-robustness (and matching the project's own convention of promoting emergent safety to explicit invariants — cf. the L-02/price>0 comments):
- Add `expect circ_in > 0` at the top of the `LpWithdraw` branch ([lp_intent.ak:163](../../shaswap/lib/shaswap/lp_intent.ak#L163)), mirroring [lp_intent.ak:188](../../shaswap/lib/shaswap/lp_intent.ak#L188).
- Optionally make `get_amount_out` total: `expect dx > 0 && fee_den > fee_num && fee_den > 0` (or return `Option`), decoupling its safety from call-site guards. No on-chain behaviour change for existing uses.

**Tests To Add:**
- Negative
  - [ ] `test fail__withdraw_circ_in_zero()` — construct (or document the infeasibility of) an all-LP-held pool with a withdraw intent and assert abort.
- Property
  - [ ] Fuzz `get_amount_out` inputs off-chain; assert it is total or returns `None` for degenerate inputs.

**Additional Notes:**
- Purely additive guards; cannot weaken any invariant or affect liveness (a withdraw against an all-LP-held pool is already infeasible). Two locations, one root cause (`defensive-division-guard`).

**Knowledge References:**
- [attacks/arithmetic.md:8-47](../../attacks/arithmetic.md#L8-L47) (Division By Zero — guard every `/` denominator with `expect d > 0`)

**What It Is:**

N/A — no profitable attack. A user could author a self-overpaying order (negative tip = bonus to themselves at a solver's expense); no rational solver settles it.

- Quoted asymmetry vs [lp_intent.ak:139](../../shaswap/lib/shaswap/lp_intent.ak#L139).
- Conservation reasoning above; the owner-output pin at [clearing.ak:233](../../shaswap/lib/shaswap/clearing.ak#L233) forces the solver to fund any positive delta.

**How To Fix:**
For symmetry with `lp_intent.fulfill` and verify-don't-trust hygiene, add `expect order.tip >= 0` in `check_one` (mirrors [lp_intent.ak:139](../../shaswap/lib/shaswap/lp_intent.ak#L139)). **Component:** settlement / clearing

**Location:**

**Quoted Code (`lib/shaswap/clearing.ak:342-361`):**
```aiken
  let tagged_outputs = list.filter(
    tx.outputs,
    fn(o) { utils.is_tagged(o, account) },
  )
  let (pool_outs, remainders) = list.partition(...)
  // ...
  let n = list.length(order_inputs)
```

**What It Is:**
`clearing.run` is the once-per-tx settlement check whose ex-unit cost bounds the achievable batch size (~40–50 orders). It traverses the full, solver-controlled `tx.outputs` twice — `list.filter` for tagged outputs ([clearing.ak:342](../../shaswap/lib/shaswap/clearing.ak#L342)) and `list.take(tx.outputs, n)` for owner payouts ([clearing.ak:357](../../shaswap/lib/shaswap/clearing.ak#L357)) — and allocates a fresh `List<(Input, Output)>` via `list.zip` ([clearing.ak:361](../../shaswap/lib/shaswap/clearing.ak#L361)) that `process` immediately destructures element-by-element.

**Why It Is Bad — Cardano Semantic Cited:**
The Plutus ex-unit budget is the hard scarcity capping batch size; `tx.outputs` is solver-controlled in length, so each redundant O(N) pass directly lowers the order ceiling (guide #12 Avoid Re-Traversals). `list.zip` materialises a new list paying cons + tuple overhead per order before `process` walks it (guide #4/#10).

**Attack Scenario:** N/A — performance only; the exact pins are unchanged.

**Proof / Evidence:** Quoted code; a baseline exists — `bench settlement__run` is size-parameterised ([clearing_test.ak:2181](../../shaswap/lib/shaswap/clearing_test.ak#L2181)).

**How To Fix:**
Drop `list.zip` by changing `process` to recurse on `order_inputs` and `owner_outputs` in lockstep (`when (is, os) is { ([], []) -> … ; ([i,..it],[o,..ot]) -> … }`). The positional owner-output binding forces the `list.take` re-walk, so leave that unless a redeemer-index binding is adopted (a design change, out of optimization scope). Preserve the exact pins and re-run the full negative + property suite; measure with `settlement__run` before/after.

**Tests To Add:**
- Benchmark
  - [ ] Re-run `bench settlement__run` at N = 1 / 25 / 50 before and after the fold; require a measured ex-unit reduction and no test regressions.

**Additional Notes:**
- **Risk: low–medium** — input/output classification is the most security-sensitive part of the validator; any change must preserve the exact partition/zip semantics. **Baseline benchmark exists**, so before/after is measurable. Carried from the prior in-tree O-02.

**Attack Scenario:** N/A — performance only; the dust band semantics are unchanged.

Asset names use the correct CIP-67-free raw hex (`4e4654` NFT, `4c50` LP, `54455354` "TEST"). Consistent with `constants.ak`.
- **L-01 builder precondition honoured:** the demo order builder sets `owner = Constr 0 [SOLVER_PKH]` = `VerificationKey(_)` ([05-post-order.sh:18-19](../../shaswap/happy_path/05-post-order.sh#L18-L19)) and `owner_stake = Some(VerificationKey(SOLVER_STAKE_PKH))` — so the demo never creates a non-reclaimable Script-owner order. Good (the production builder must do likewise).
- **Curve parity:** `06-settle.sh` computes `received = (res_b*sell*g)//(res_a*fee_den+sell*g)` ([06-settle.sh:46](../../shaswap/happy_path/06-settle.sh#L46)) — the same floor as on-chain `get_amount_out` — and asserts the floor `sell*num >= limit*den`. The on-chain validator re-verifies, so a parity bug yields a rejected tx, never a bypass.
- **Network correctness:** all scripts use `--testnet-magic "$NET_MAGIC"` with `NET_MAGIC=1` (preprod). No mainnet path. `deployment.json` `network_id=0`. (A mainnet cut must flip these.)
- **Validator-hash baked vs `plutus.json`:** the unparameterised `settlement` hash matches `plutus.json` exactly (`a305a3cf…`); `order(S)` reproduces from current source; `pool(S)`/`lp_intent(S)` are **stale** (I-06).
- **Reference UTxOs:** most scripts read live refs from `work/refs.json`; `11-reclaim-lp-intent.sh` hardcodes one (I-06).
- **Collateral/fee/change:** `06-settle.sh` selects pure-ADA funding + a distinct pure-ADA collateral and uses `--change-address "$SOLVER_ADDR"` (the solver's residual = tips); `cli transaction build` auto-estimates fees. No hardcoded output indexes that affect on-chain validity (the validator binds by positional/NFT rules it enforces itself).

**On-chain reachability of off-chain assumptions:** the design is "untrusted solver, verify-only on-chain," so essentially no security assumption is delegated off-chain. The one off-chain-only invariant is the order/intent `owner` VK shape (L-01), which the demo builder honours.

**Final question — Is the validator safe if a malicious user bypasses the official builder? — Yes.** Safety is enforced on-chain by value conservation + exact pins + the curve/price pin + the one-shot NFT singleton, not by these scripts. A handcrafted transaction cannot extract trader funds, pool reserves, or free tokens (see §3.8). The off-chain findings (I-06) are deployment-harness hygiene, not bypass surfaces.
