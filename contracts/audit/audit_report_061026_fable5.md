## 3. Contract Overview

ShaSwap is a fully-decentralized, non-custodial, MEV-resistant batch-auction DEX. The protocol's pieces:

- **`settlement`** — an **unparameterised** withdraw-0 staking script that is the immutable trust anchor `S`. Its `withdraw` handler runs `clearing.run`, learning its own credential `S` at runtime as the withdraw account and enumerating every input/output whose stake credential is `S`. Its `publish` handler permits *only* `RegisterCredential` (so the anchor can be brought into existence) and denies de-registration/delegation, keeping `S` immortal and undelegatable. `else -> fail`.
- **`order`** (parameterised by `S`) — a user order. `Settle` defers to the anchor (self-checking its own `S` tag + the withdraw-0 presence); `Reclaim` is owner-signature-only. `else -> fail`.
- **`pool`** (parameterised by `S`) — a constant-product pool. `PoolSettle` owns the curve invariant `k_after ≥ k_before` with a static fee and self-enforces its own `S`-tag + NFT + held-LP continuity (audit H-01); `LpAction` runs a value-derived LP deposit/withdraw under a mutual-exclusion guard against settlement; `ClosePool` tears down a never-seeded pool (creator signature + full NFT/LP burn). `else -> fail`.
- **`pool_mint`** (parameterised by a seed `OutputReference`) — a one-shot pool create/close minting policy. `Create` mints exactly `{NFT:1, LP:total_lp}` into a validated pool UTxO; `Close` is burn-only. `else -> fail`.
- **`lp_intent`** (parameterised by `S`) — a batcher-fulfilled LP deposit/withdraw intent at an *enterprise* (non-`S`) address so the anchor never enumerates it. `Fulfill` settles one intent against its pool (asserting `!withdrawal_present(S)` so the per-share backing always runs), pinning the owner payout and the pool value exactly; `ReclaimLp` is owner-signature-only. `else -> fail`.

**Protocol flow narrative.** *Creation:* a pool is created by the one-shot `pool_mint` policy (consuming a unique seed), which validates the `PoolDatum` (external distinct pair, fee in range, VK creator, ≥ `pool_min_ada`) and forces the NFT + full LP supply into one pool UTxO. Orders and LP-intents are plain payments to their script addresses (no validator runs on creation). *State transitions:* a settlement spends the pool + a batch of orders, paying each order its bound output at one uniform price and absorbing the residual into the pool; LP deposits/withdraws move reserves and LP between pool and user. *Terminal:* `ClosePool` (pre-seed only) burns the NFT + full LP; post-seed pools are immortal (the locked `min_liq` can never be reassembled).

- **Major assets / tokens:** per pool, a unique NFT (`#"4e4654"` = "NFT") and an LP fungible (`#"4c50"` = "LP", supply `total_lp = 2⁶³−1` held-in-pool), both under the pool's one-shot policy; plus the two externally-traded assets `(asset_a, asset_b)` (either may be ADA).
- **Expected transaction shapes:** (settlement) 1 pool input + N S-tagged order inputs + the withdraw-0 for `S` → N owner outputs (first N) + 1 pool output + remainder outputs; (LP action / LP-intent fulfill) 1 pool input + 1 LP UTxO → 1 pool output + 1 owner output; (create) seed input + mint → 1 pool output; (close) pool input + burn.
- **Off-chain assumptions:** the solver/batcher computes the clearing off-chain (out of scope; not in target); builders must set `owner`/`creator` to VK credentials and place pools at the `S`-tagged address (see §4, §11, L-01/L-02).
- **User roles:** order owner, LP-intent owner, pool creator (all by VK signature). **Admin roles:** none (no admin/upgrade key; hyperstructure design). **Hyperstructure assumptions:** immortal undelegatable anchor `S`; immortal post-seed pools; non-custodial reclaim liveness — see §9.

### 3.8 Builder-Bypass Question

**Is the validator safe if a malicious user bypasses any official off-chain builder? — Yes, for funds; Partially, for self-lock.** Every economic outcome is enforced on-chain against a handcrafted transaction: settlement pins every owner payout, remainder, and the pool by exact value-transform with `mint == 0`, so an attacker who hand-builds a settlement can only produce one that pays each order at least its limit at a single uniform price and nets the solver only the posted tips — or the transaction fails. Orders/pools/intents are authenticated by the `S` stake tag and one-shot NFTs, not by address alone, so forged or twin UTxOs are rejected (§10, §19). The single residual exposure to bypassing a builder is *self-inflicted*: a user who hand-builds an order/LP-intent with a Script-credential `owner` (L-01) or a pool placed off the `S`-tagged address (L-02) can lock *their own* funds or self-grief their own pool — never another principal's funds. No bypass yields theft, unauthorized mint, or settlement mis-pricing.

### L-01 Verification-key `owner` is an off-chain-only builder invariant: a Script-credential owner yields a settleable-but-unreclaimable order / LP-intent

**Severity:** Low

**Confidence:** Confirmed

**Status:** Design Tradeoff

**CWC ID:** [CWC-043](../../../taxonomy.md) (Off-Chain Builder Trust Gap)

**Root Cause:** `vk-owner-enforced-off-chain-only`

**Component:** order validator + lp_intent validator (owner-credential well-formedness; reclaim path)

**Location:**
- [`lib/shaswap/spend.ak:72-75`](../../../contracts/shaswap/lib/shaswap/spend.ak#L72-L75) (`order_reclaim` — the only VK gate; `lp_intent.reclaim` delegates here)
- [`lib/shaswap/utils.ak:32-42`](../../../contracts/shaswap/lib/shaswap/utils.ak#L32-L42) (`is_payout_output` — settle path accepts any owner credential)
- [`lib/shaswap/clearing.ak:174`](../../../contracts/shaswap/lib/shaswap/clearing.ak#L174) (settle uses owner without a VK assertion)
- [`README.md:32-40`](../../../contracts/shaswap/README.md#L32-L40) (documents the off-chain requirement)

**Quoted Code (`lib/shaswap/spend.ak:72-75`):**
```aiken
/// Order `Reclaim`: owner signature alone (§5.1, non-custodial).
pub fn order_reclaim(owner: Credential, tx: Transaction) -> Bool {
  expect VerificationKey(vkh) = owner
  list.has(tx.extra_signatories, vkh)
}
```

**Quoted Code (`lib/shaswap/utils.ak:32-42`, the settle-side payout that does NOT require a VK owner):**
```aiken
pub fn is_payout_output(
  o: Output,
  owner: Credential,
  owner_stake: Option<Credential>,
) -> Bool {
  let stake = when owner_stake is {
    Some(c) -> Some(Inline(c))
    None -> None
  }
  o.address == Address { payment_credential: owner, stake_credential: stake } && o.reference_script == None
}
```

**What It Is:**
`OrderDatum.owner` and `LpIntentDatum.owner` are typed `Credential`, so either a `VerificationKey` or a `Script` credential is type-valid. On the settle/fulfill path the owner is consumed only via `is_payout_output`, which writes the credential straight into the payout `Address` with no `expect VerificationKey` — so a Script-credential owner settles/fulfills fine. The reclaim path, by contrast, hard-requires a VK (`expect VerificationKey(vkh) = owner`). Because Plutus V3 spend validators do not run when a UTxO is created, and the only creation-time script (`pool_mint`) validates the `PoolDatum`, not order/intent datums, nothing on-chain rejects a Script-credential owner at order/intent posting. The well-formedness of `owner` is therefore enforced only by the off-chain builder (README.md:36-37), which the in-repo `happy_path` builders honor.

**Why It Is Bad — Cardano Semantic Cited:**
An order or LP-intent whose `owner` is a Script credential can be settled/fulfilled but never reclaimed: `order_reclaim` / `reclaim` crash on `expect VerificationKey(vkh) = owner` for any non-VK owner. The Cardano semantic is *validators do not run on UTxO creation, only on spend* — so a malformed owner cannot be rejected at posting time; it is only caught at the spend, where reclaim becomes impossible. If such a UTxO is posted and the solver never settles it (unattractive limit, or it ages out), the funds are permanently locked. This is a *value-leak / self-lock* (the victim is whoever built the malformed order), not principal theft of another party.

**Attack Scenario:**
A user (or a buggy third-party front-end) hand-assembles an order UTxO at the order address (correctly `S`-tagged) with an inline `OrderDatum` whose `owner` is `Constr 1 [ScriptHash]` (a Script credential) instead of `Constr 0 [VKHash]`. The ledger accepts the plain payment to the script address (no validator runs on creation). The order now holds the user's tokens + tip + min-ADA. If the solver never settles it (its `limit` is set to a price no solver will hit, or it simply expires), the owner attempts `Reclaim` — and the transaction fails phase-2 because `expect VerificationKey(vkh) = owner` crashes on the Script owner. The funds are bricked. The same path exists for `LpIntentDatum.owner` via `ReclaimLp`. No other principal's funds are reachable: the settle path still pins the payout address from the datum and value-conserves, so a Script-owner order that *is* settled simply pays out to that script address.

**Proof / Evidence:**
- Quoted code above (the VK gate on reclaim vs. the credential-agnostic settle payout) — primary evidence.
- `OrderDatum.owner: Credential` ([types.ak:41](../../../contracts/shaswap/lib/shaswap/types.ak#L41)); `lp_intent.reclaim` delegates to `spend.order_reclaim` ([lp_intent.ak:240-242](../../../contracts/shaswap/lib/shaswap/lp_intent.ak#L240-L242)).
- Cross-reference: [`attacks/off_chain.md`](../../../attacks/off_chain.md) (Builder Assumption Not Enforced On-Chain) and [`ctf/bank_04_lifecycle.md`](../../../ctf/bank_04_lifecycle.md) (validators don't run on UTxO creation).
- Negative test already present: `reclaim_script_owner() fail` ([clearing_test.ak:438](../../../contracts/shaswap/lib/shaswap/clearing_test.ak#L438), [lp_intent_test.ak:1005](../../../contracts/shaswap/lib/shaswap/lp_intent_test.ak#L1005)) — proves a Script-owner reclaim fails (i.e. the lock).

**How To Fix:**
Primary: keep the documented off-chain requirement (README.md:36-37) and have every builder set `owner` to a verification-key hash (`Constr 0 [vkh]`) — the `happy_path` scripts already do this ([05-post-order.sh](../../../contracts/shaswap/happy_path/05-post-order.sh), [10-post-lp-intent.sh](../../../contracts/shaswap/happy_path/10-post-lp-intent.sh)). Optional defense-in-depth (removes the asymmetric settleable-but-locked window): reject a non-VK owner on the settle path too, by adding `expect VerificationKey(_) = order.owner` inside `check_one` ([clearing.ak:137-174](../../../contracts/shaswap/lib/shaswap/clearing.ak#L137-L174)) and an analogous guard in `lp_intent.fulfill`, so a Script-owner UTxO is uniformly *rejected* (fail-closed) rather than silently lockable. The cost is one `expect` per order; the benefit is symmetry (a malformed order can never be settled OR reclaimed, so it is never silently bricked after value moves).

**Tests To Add:**
- Negative
  - [ ] Already present: `reclaim_script_owner` fails (order + lp_intent). Keep.
  - [ ] If adopting the fix: `settle_script_owner_rejected` — a settlement including a Script-owner order must fail in `check_one` (currently it would *succeed*, which the fix changes).
- Property
  - [ ] Fuzz `OrderDatum.owner` over VK vs Script credentials; assert reclaim succeeds iff VK, and (post-fix) settle succeeds iff VK.

**Additional Notes:**
- Tiering: class default for an off-chain builder trust gap (CWC-043) is Medium; the §4 Documented Trust Model truth table applies a one-tier demotion because the requirement is documented (non-verbal, README.md:36-37) with no roadmap removal → **Low**, Status "Design Tradeoff". (value leak / self-lock; principal of other parties preserved.)
- This is the prior audit's "L-01" condition (the in-code `audit L-01` markers and README para document it). It remains a documented tradeoff, not a regression — the on-chain half (the `owner_stake == S` self-poison) was already moved on-chain in `check_one` ([clearing.ak:155-164](../../../contracts/shaswap/lib/shaswap/clearing.ak#L155-L164)).
- Self-inflicted only: an attacker cannot use this to lock a *different* user's funds.

### L-02 Pool placement at the `S`-tagged settlement address is an off-chain-only creation invariant

**Severity:** Low

**Confidence:** Suspected

**Status:** Design Tradeoff

**CWC ID:** [CWC-023](../../../taxonomy.md) (Cross-Validator Incoherence)

**Root Cause:** `off-chain-only-pool-placement`

**Component:** pool_mint (`mint.create`) / pool spend (`pool_settle`)

**Location:**
- [`lib/shaswap/mint.ak:60-68`](../../../contracts/shaswap/lib/shaswap/mint.ak#L60-L68) (create can validate the datum + min-ADA but not the `S`-tag placement)
- [`lib/shaswap/spend.ak:88-96`](../../../contracts/shaswap/lib/shaswap/spend.ak#L88-L96) (audit H-01 — `pool_settle` self-enforces the `S`-tag, the on-chain mitigation)
- [`validators/pool_mint.ak:10-21`](../../../contracts/shaswap/validators/pool_mint.ak#L10-L21) (policy parameterised by `seed` only — cannot see `S`)

**Quoted Code (`lib/shaswap/mint.ak:60-68`):**
```aiken
  // (L-03) the pool must hold at least the per-UTXO min-ADA overhead that
  // `reserve_of` carves out — otherwise its ADA reserve would be negative and the
  // first deposit / every settlement against it would be infeasible (self-brick).
  // This is the on-chain half of the placement invariant; the OFF-CHAIN builder is
  // still responsible for placing the pool at the `pool(S)` address tagged `S` (the
  // mint policy is parameterised only by the seed and so cannot see `S` — but the
  // one-shot NFT + post-creation address continuity make a mis-placement a creator
  // self-grief, never a theft of others' funds — audit L-03).
  expect assets.lovelace_of(pool.value) >= pool_min_ada
```

**Quoted Code (`lib/shaswap/spend.ak:88-96`, the audit-H-01 on-chain mitigation):**
```aiken
  // (audit H-01) self-enforce that our own input is S-tagged — parity with
  // `order_settle` (which self-tags too). The settlement anchor enumerates pools by
  // the `S` tag (`clearing.run`), so an UNtagged pool placed at the `pool(S)` payment
  // credential (mint.create can't see `S`, so it can't reject the placement) would be
  // spendable here yet INVISIBLE to the anchor's full-value pin — letting a solver
  // strip its held LP (then drain reserves via `LpAction`). Requiring the S tag forces
  // every `PoolSettle`'d pool to be enumerated AND fully value-pinned by the anchor,
  // and removes the on-chain reliance on the off-chain pool-placement invariant (§5.4).
  expect utils.is_tagged(own.output, s)
```

**What It Is:**
A pool UTxO is created by the `pool_mint` policy, which is parameterised only by the seed `OutputReference` and therefore cannot see the settlement credential `S`. `mint.create` validates the pool's NFT identity, external distinct pair, fee range, VK creator, and ≥ `pool_min_ada` lovelace — but it cannot assert the pool lands at the `pool(S)` payment credential with stake tag `Some(Inline(S))`. Because spend validators do not run at UTxO creation, correct placement at the `S`-tagged pool address is a creation-time invariant enforced off-chain by the builder.

**Why It Is Bad — Cardano Semantic Cited:**
The Cardano semantic is two-fold: *validators do not run on UTxO creation* (so the mint policy is the only creation-time gate, and it can't see `S`), and *the settlement anchor enumerates the protocol set by stake-credential tag* (`is_tagged`). A pool placed at the `pool(S)` payment credential but **without** the `S` stake tag would be invisible to the anchor's full-value pin. Absent a mitigation, a solver could spend such an untagged pool via `PoolSettle` while it stays unseen by the anchor's conservation pin — stripping its held LP and then draining reserves via `LpAction`. **This is mitigated on-chain** by audit H-01: `pool_settle` self-enforces `expect utils.is_tagged(own.output, s)`, so an untagged pool is simply un-`PoolSettle`-able; combined with the one-shot NFT and post-creation address continuity, a misplacement becomes *creator self-grief* (the creator's own pool is unusable), never theft of another party's funds.

**Attack Scenario:**
A builder (or attacker) creates a pool whose output is placed at the `pool(S)` payment credential but with a *different* (or absent) stake credential. The mint succeeds (`mint.create` can't check placement). Now: (a) the misplaced pool cannot be `PoolSettle`'d — `pool_settle` requires `is_tagged(own.output, s)` (H-01), so it fails; (b) it cannot be enumerated by the anchor (the anchor filters by `is_tagged`), so no settlement can pull value from it; (c) `LpAction` and `ClosePool` still pin NFT + held-LP continuity and (for close) require the creator's VK signature. The net effect is a pool that only its creator can interact with (LP/close), holding only the creator's own seed value — a self-grief. No third party's funds are reachable.

**Proof / Evidence:**
- Quoted code above: `mint.create` documents the off-chain placement responsibility; `pool_settle` (H-01) is the on-chain mitigation that closes the theft path.
- `pool_mint` is parameterised by `seed: OutputReference` only ([pool_mint.ak:10](../../../contracts/shaswap/validators/pool_mint.ak#L10)).
- Cross-reference: [`attacks/state.md`](../../../attacks/state.md) (Lifecycle Bypass At UTxO Creation) and [`ctf/bank_04_lifecycle.md`](../../../ctf/bank_04_lifecycle.md).
- Negative tests present: `pool_settle_non_s_tag_rejected`, `pool_settle_enterprise_rejected`, `pool_settle_non_s_tag_rejected_even_if_lp_kept` ([clearing_test.ak:1099-1131](../../../contracts/shaswap/lib/shaswap/clearing_test.ak#L1099-L1131)) — prove an untagged pool is un-settleable.

**How To Fix:**
No on-chain fix is required to prevent theft (H-01 already closes it). The residual is liveness/UX: a misplaced pool wastes the creator's seed. Keep the documented off-chain requirement (place the pool at the `pool(S)` address, tagged `S`) in the README/spec and the pool-creation builder; the `04-create-pool.sh` script already targets the correct address. If desired, a post-deploy ledger check (assert the created pool UTxO is at the `pool(S)` address with the `S` stake tag before considering the pool live) gives the creator an early failure instead of a silent self-grief.

**Tests To Add:**
- Negative
  - [ ] Already present: `pool_settle_non_s_tag_rejected` / `_enterprise_rejected` — keep (they prove the H-01 mitigation).
- Positive
  - [ ] A creator-only LP/close flow on a (hypothetically) misplaced pool returns only the creator's seed — documents the self-grief boundary.

**Additional Notes:**
- Tiering: CWC-023 (cross-validator incoherence) default Medium; documented (non-verbal) off-chain enforcer with no roadmap removal → one-tier demotion → **Low**, Status "Design Tradeoff". The audit-H-01 on-chain S-tag check makes this effectively *not exploitable for theft* — the residual is creator self-grief only. Confidence "Suspected" reflects that no third-party-loss path exists (the only "exploit" is self-inflicted).
- This is a Phase 5d off-chain-only-enforcement auto-finding; it is the pool row of the §11 lifecycle table.

**Quoted Code (`validators/order.ak:12-24` — the untested wrapper):**
```aiken
validator order(settlement_cred: Credential) {
  spend(
    datum: Option<OrderDatum>,
    redeemer: OrderRedeemer,
    utxo: OutputReference,
    self: Transaction,
  ) {
    expect Some(d) = datum
    when redeemer is {
      Settle -> spend.order_settle(self, utxo, settlement_cred)
      Reclaim -> spend.order_reclaim(d.owner, self)
    }
  }
```

**What It Is:**
The five validators are thin wrappers that `expect Some(d) = datum`, dispatch on the redeemer constructor, and fall through to `else -> fail`. The test suite drives the *library* functions (`spend.order_settle`, `spend.order_reclaim`, `lp_intent.fulfill`, `mint.create`, `clearing.run`, …) directly — never the validators' own `spend` / `mint` signatures — for `order`, `lp_intent`, and `pool_mint`. A repo-wide search confirms the only validator-entrypoint drives are `pool.pool.spend` (the `LpAction` arm only, in `pool.test.ak`) and `settlement.settlement.publish` (in `settlement.test.ak`). So for `order`, `lp_intent`, and `pool_mint`, the wrapper's `expect Some(d) = datum` no-datum abort and the redeemer `when` dispatch arms are never executed under a constructed `Transaction`; `pool`'s `PoolSettle`/`ClosePool` arms and `settlement.withdraw` are likewise undriven at the wrapper layer.

**Why It Is Bad — Cardano Semantic Cited:**
Library-level tests cannot catch a wrapper-level mis-wiring: a swapped redeemer→function dispatch, a missing `expect Some` (a V3 spend handler that forgets to reject a `None` datum — the ledger delivers `None` for a `NoDatum` script input), or an `else` arm that does not `fail`, would all pass the lib tests while shipping a broken validator. This is a test-methodology gap, not an on-chain defect — the wrappers as written are correct (verified by reading them) — but the gap means a future edit to a wrapper is unguarded by the suite.

**Attack Scenario:**
No direct attack (the wrappers are presently correct). The risk is regression: e.g. a refactor that changes `order`'s dispatch to `Settle -> spend.order_reclaim(...)` (a copy-paste slip) would not be caught by any existing test, because no test invokes `order.order.spend` with a `Settle` redeemer and a constructed transaction. It is recorded so a future auditor/maintainer knows the wrapper layer is unverified by the suite.

**Proof / Evidence:**
- Quoted wrapper above; `grep` for `order.order.spend` / `lp_intent.lp_intent.spend` / `pool_mint.pool_mint.mint` over the test tree returns zero matches; the only wrapper drives are `pool.test.ak` (LpAction) and `settlement.test.ak` (publish).
- Cross-reference: [`attacks/code_quality.md`](../../../attacks/code_quality.md) (test methodology / dispatch) and [`patterns/test_fixture_variance.md`](../../../patterns/test_fixture_variance.md) (the suite is only as adversarial as its drives allow).

**How To Fix:**
Add a thin wrapper-level test per validator that constructs a `Transaction` and calls the validator's own entrypoint (`order.order.spend(Some(d), Settle, utxo, tx)`, `…Reclaim…`, the `pool` `PoolSettle`/`ClosePool` arms, `pool_mint.pool_mint.mint(Create, pid, tx)` / `Close`, and a `settlement.settlement.withdraw` happy drive). Mirror the pattern already used in `pool.test.ak` and `settlement.test.ak`. Include at least one `None`-datum negative per spend wrapper (`pool_spend_no_datum` already does this for `pool`) to cover the `expect Some(d) = datum` abort.

**Tests To Add:**
- Positive
  - [ ] `order.order.spend(Some(d), Settle, utxo, tx)` happy + `Reclaim` happy through the wrapper
  - [ ] `lp_intent.lp_intent.spend(...)` `Fulfill` + `ReclaimLp` through the wrapper
  - [ ] `pool_mint.pool_mint.mint(Create, pid, tx)` + `Close` through the wrapper
  - [ ] `pool.pool.spend` `PoolSettle` + `ClosePool` arms (only `LpAction` is currently driven)
  - [ ] `settlement.settlement.withdraw` happy drive
- Negative
  - [ ] `None`-datum abort per spend wrapper (extend `pool_spend_no_datum` to order/lp_intent)
  - [ ] An unexpected `ScriptPurpose` hits `else -> fail` (one per validator)

**Additional Notes:**
- Informational only — the wrappers are presently correct; this is a coverage/methodology note, not a vulnerability. It does not reduce the §16 Testing score (which is computed over redeemer constructors, all of which are covered at the lib layer).
- `pool.test.ak` and `settlement.test.ak` show the team already knows this pattern; extend it to the other three validators.

**Not applicable.** The protocol consumes no reference inputs (G-06 empty) and reads no external price feed. The clearing price is supplied by the (untrusted) solver in `SettlementRedeemer` and is *pinned to the pool's own constant-product curve* by the `k_ok`/`pin_ok` two-sided check in `pool_settle` plus the per-order floor — it is not read as a spot oracle for any external decision. There is no `last_updated`/timestamp datum field anywhere. A solver cannot move the protocol's settlement logic by manipulating a price feed because there is no feed; the only price freedom a solver has is bounded above by `k` (can't pay out more than the curve allows) and below by each order's limit + the curve floor.

The production solver/batcher is **not in the target** (§3.7). The in-target off-chain code is the `happy_path/*.sh` cardano-cli bootstrap/test scripts (20 scripts, ~1.6k lines). Reviewed as supporting evidence:

- **Network magic / id:** preprod throughout (`env.sh`).
- **Hardcoded indexes:** none trusted on-chain — the validator locates outputs by identity (NFT, address, `BoundDatum.order_ref`), never by a redeemer-supplied position; the off-chain scripts build sorted/positional bodies but the validator verifies, not trusts.

- **Collateral:** the script context (`cardano/transaction.Transaction`) exposes no collateral inputs, so collateral hygiene is correctly an off-chain concern (not a validator finding; see §19 and CWC-044).
- **Minor builder note (no security impact):** `11-reclaim-lp-intent.sh` hardcodes a reference-script txid instead of reading `work/refs.json` the way `06-settle.sh` does — a test-script staleness nit, not a protocol issue.
